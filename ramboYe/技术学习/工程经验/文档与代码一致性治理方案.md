**目标：减少手写文档对实现事实的重复描述，让必须保留的说明能追溯到来源、发现变更，并在被 Agent 用于决策前重新核实。**

本文是具体实施方案。未检查业务仓库，未安装脚本或修改 Agent 规则；路径、字段和案例均为设计示例。

**一、先按问题确定依据**

“所有冲突都以代码为准”会把实现错误固化成规范。需要先明确正在回答什么问题：

| 问题 | 主要依据 | 文档承担的职责 |
| --- | --- | --- |
| 当前分支怎么实现？ | 该分支当前源码、配置及必要的验证结果 | 提供代码入口和解释 |
| 系统应该怎样表现？ | 已批准需求、接口契约、架构决定和验收条件 | 明确意图与约束 |
| 线上现在怎样运行？ | 部署版本、实际生效配置和对应运行证据 | 记录环境、版本、观测时间 |
| 为什么当时这样设计？ | 决策记录、评审和历史证据 | 保留备选方案、取舍及重评条件 |

源码和契约冲突时，报告不一致并判断应修哪一侧；不能自动修改契约去迎合实现。一个环境的运行证据也不能外推为所有环境的状态。

**二、把文档分成四类，各用一种维护方式**

| 类型 | 内容 | 维护方式 |
| --- | --- | --- |
| 导航 | 模块入口、符号、源码和测试位置 | 只保存坐标与少量稳定说明，检查链接和符号是否存在 |
| 派生参考 | 字段表、服务列表、配置项、接口结构 | 从选定的权威来源生成，标明来源版本，禁止手工维护生成区 |
| 决策与经验 | 设计理由、兼容边界、排障假设、重评条件 | 手工或 Agent 辅助维护，绑定证据并复核 |
| 历史记录 | 某次故障、发布或方案的现场 | 保留当时版本与环境，明确是历史，不冒充当前说明 |

例如：如果项目先编写协议 Schema 再生成代码，应从 Schema 生成接口参考；如果由代码定义接口，则从代码生成。先确定生成方向，避免双向修改循环。

目录和字段可以生成，设计理由不能可靠地从最终代码推导出来。无法生成但又有阅读价值的架构说明可以保留，并明确抽象层次与复核责任。

**三、让每条关键说明能定位到证据**

建议先在重要决策文档上使用以下最小结构，不必一次迁移所有笔记：

```yaml
id: decision-reward-idempotency
kind: decision
scope: 奖励领取模块
owner: reward-team
sources:
  - repo: game-server
    path: internal/reward/claim.go
    symbol: ClaimReward
  - repo: game-server
    path: internal/reward/claim_test.go
    symbol: TestClaimRetry
last_reviewed_revision: '<实际复核过的提交号>'
review_status: reviewed
```

正文保留四项：结论、原因、证据与验证方法、什么变化后需要重新评估。字段名是建议格式，并非现有工具协议。

使用“仓库 + 路径 + 符号”作为主要定位方式。行号适合当次定位，但会随编辑变化；提交号固定历史现场，不代表当前版本仍然适用。跨仓库知识应分别记录各仓库版本。

**四、通过变化触发复核，减少依赖记忆**

第一版检查工具只承担可以机械判断的工作：

1. 检查文档引用的文件、符号及本地链接是否存在。
2. 在 PR 中，用合并基点到候选合并结果的差异找出新增、修改、删除和重命名的文件，匹配文档声明的依赖。
3. 对匹配的文档生成“待复核清单”，列出变化来源，要求更新内容或说明为何结论仍成立。
4. 重新生成派生参考，检查提交的生成物是否与生成结果一致。

不能用“文档文件也被修改过”代替复核；改一个日期不足以证明内容正确。复核记录应说明变化是否影响结论、依据什么证据，以及核验的是哪个版本。

进入日常读取后，可以保存每篇文档复核时依赖文件的路径与内容摘要，读取前与目标工作区比较。无关文件变更不影响该文档；相关文件或文档正文变化后重新复核。依赖包含目录匹配规则时，也要检查文件集合的新增、删除和重命名。工作区有未提交变更时，按实际文件内容判断，不能只看 HEAD。

**变化只说明需要复核，不证明文档错误；摘要相同只说明已声明的依赖未变，不证明所有隐含前提仍然成立。** 跨模块变化、外部系统和遗漏依赖仍需要任务内验证。第一版以文件粒度检查即可，误报显著增加后再考虑符号粒度。

**五、明确哪些失败阻断，哪些只是提醒**

| 检查结果 | 建议处理 |
| --- | --- |
| 生成参考与来源不一致、必需来源失踪 | 阻断对应检查，修复来源或生成流程 |
| 接口契约、兼容约束等关键文档涉及的来源改变 | 要求完成复核后通过 |
| 一般背景说明受到关联代码变更影响 | 标为待复核，可先告警，避免所有代码改动都被文档阻塞 |
| 外部证据无法访问、来源版本无法确认 | 标为未知，不能标成已验证 |
| 历史记录引用旧实现 | 保持历史版本身份，不机械重写成当前事实 |

有效期适合触发周期复核，不能证明语义过期。频繁变化的运行配置应提高复核频率，稳定设计理由按前提变化触发；不要给所有知识同一个自动删除期限。

**六、Agent 的读取流程要回到源码和现场**

建议把下面短规则作为待采用的任务协议，工具负责提供来源信息与变化状态：

```text
1. 从知识索引定位当前任务相关说明及其来源。
2. 使用说明中的关键结论前，打开对应来源，核对版本、环境和适用条件。
3. 待复核或来源未知的说明可作为探索线索，不作为已验证事实。
4. 区分当前实现、预期契约和线上状态；冲突时报告两侧证据。
5. 验证完成后，更新原知识或记录无需修改的理由；重复结论不另建副本。
```

硬约束文档即使待复核，也不能被静默忽略。涉及改变团队已批准边界的情况，应明确解决冲突后再执行相关变更。

仅将以上规则写进 Prompt，不能保证执行稳定。关键门禁应由现有检查流程调用；工具缺失或失败时应如实报告未检查。

**七、用一个例子串起来**

假设文档原来写：“奖励领取调用 A，然后写 B，最后更新字段 C。”这几步与实现高度重复，重构后很容易过期。

可以改成：

```text
导航：奖励领取入口见 ClaimReward，重复请求行为见 TestClaimRetry。
决策：客户端可能重试同一次领取；需要确保同一领取标识不会重复发奖。
依据：对应需求、故障记录和幂等回归测试。
适用范围：指定领取接口及其重试链路。
重新评估：领取标识、持久化机制或事务边界发生变化时。
```

这里的“不得重复发奖”是示例中的预期约束。若新代码改坏幂等行为，应该由回归测试报错并修实现；若产品正式允许新一轮领取，则更新契约、标识语义、测试和决策理由，保留旧决策的历史身份。

文档记录检查方向和设计依据，测试验证可执行边界。测试通过只覆盖它所验证的场景，不能证明整个说明永远正确。

**八、Obsidian 与项目仓库如何分工**

对当前使用方式，建议：

- Obsidian 收藏原文与学习总结，保留它们作为阅读资料的身份；文章中的结论不自动成为项目规则。
- 与代码强相关、需要跟随分支演进的决策和操作说明，优先在项目仓库保留权威版本，以便和代码一起审阅。
- Obsidian 中对应的项目入口笔记链接到该权威版本，避免再维护一份相同的当前实现说明。
- 如果必须在两处阅读全文，使用单向生成或同步，标清源与派生副本；禁止两处各自手改。
- 若团队暂时只能把权威文档放在 Obsidian，应显式记录项目依赖与版本，并由项目检查流程读取这些映射；代价是跨系统同步和分支管理更复杂。

**九、建议的落地顺序与验收**

先选一个经常修改且文档容易过期的模块试点：盘点重复事实、确定权威来源、将细节改成导航或生成参考，再补少量关键决策的来源字段，最后接入变化检测与复核流程。

试点至少验证五种情况：相关代码改动能发现受影响文档；无关改动不触发全库复核；文件删除或重命名不会漏检；生成参考被手改能发现；文档仍成立时可以凭证据完成复核而不制造无意义改写。

观察误报量、复核耗时、失效文档被采用的次数，再决定扩大范围。无需在第一步建设向量库、知识图谱或独立 Memory Runtime。
