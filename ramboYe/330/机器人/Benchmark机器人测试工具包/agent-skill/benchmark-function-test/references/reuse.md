# 功能资料积累与复用

这是 Agent 的工作流程，不是后台自动学习服务。客户端只负责提交和取证；Agent 负责发现、核验、保存和下次读取。不要求预先覆盖全部功能，不引入 RAG 或新测试 DSL。

## 组织：领域索引、公共能力、具体测试

领域分类保留活动、联盟、玩家系统、编队、地图、远征、战斗等，可交叉引用；默认作为笔记标签和 `00-索引.md` 的分组，不要求每个领域都有独立文件。

- 首次测试有值得复用的信息时，优先写一份精简功能笔记，内部记录共同准备与特有操作。不强制同时建立领域、公共能力、案例三套文档。
- 实际出现跨功能复用需求时，再提取可独立核验的公共能力，原案例保留链接和特有内容；不因理论上可能通用就批量拆分。领域仍可检索原笔记中的准备步骤，无须等待独立能力文档。
- 公共能力可以放在 `公共能力/<能力名>.md`，案例可以放在 `案例/<功能名>.md`；这些是按需扩展的落点，不是必建结构。条目多到影响导航时才拆独立领域索引。
- 既有资料继续引用，不为统一目录搬动、重写或合并历史文件。跨领域能力只维护一份正文，避免复制后分别过期。

每项公共能力除来源和验证条目外，记录：

- **目标状态与适用条件**：准备完成应满足什么，适用于哪些角色身份、活动阶段、地图或赛季。
- **依赖与参数来源**：依赖哪些能力、需要哪些输入；记录条件和参数来源，不固定某次测试的联盟 ID 或角色 ID。
- **实际操作与完成核验**：现有协议、GM、LocalLogic 或 Block；核验哪些状态，异步变化何时才算完成。
- **副作用与复用限制**：是否影响联盟/地图等共享状态、是否可重复、是否需要隔离，以及已知清理方式；未知项明确注明，不凭模板自动清理。

以下只说明组织关系，不代表已验证 gs 的全部远征前置条件：

```text
联盟领域 → 加入联盟并核验成员状态
                      ↓
远征领域 → 进入远征并核验资格、赛季和地图状态
                      ├→ 攻打建筑 A 的特有条件、操作与断言
                      └→ 占领区域的特有条件、操作与断言
```

第一次测试攻打建筑 A 时，在同一笔记记录联盟准备和进入远征的核验事实；以后测试占领区域时，从领域分组检索这些步骤，确认共性后再提取公共能力并引用，不要求具体功能相同。分类或名称相近不等于条件相同，不将不同活动的开启方式、不同赛季的入场方式强行合并。

## 开始：先找资料，没有则自行发现

使用用户配置的知识目录；若设置 `BENCHMARK_AGENT_DATA_DIR`，资料目录为其下 `Benchmark功能测试/`，索引为 `00-索引.md`。若用户使用 Obsidian，可在 vault 中建立 `AI工具链/Benchmark功能测试/` 并将变量指向 vault 根；不得假定固定 home 路径。索引只列领域、能力/功能名、别名、入口符号及笔记链接，不复制测试细节。先用功能名、函数名或协议名定位相关领域，再查公共能力及其依赖；没有同名案例仍须查共同前置能力。不全量展开无关领域。按需定向检索索引和该目录，不把整个资料库载入上下文。目录不存在表示尚未积累，可以直接开始首次发现；读取失败不等于没有资料。

命中资料后按条目核对来源与适用条件。Agent 沿能力依赖组织准备顺序，检测循环、缺失和互相冲突的条件；发现冲突先分析，不机械拼接。当前状态已满足且核验通过的准备可跳过；同一目标状态及适用条件下的共享依赖可合并执行。前一步或其他用例可能破坏条件时重新核验，不能因本轮执行过就认定持续有效。没命中或资料不适用时，使用现有源码搜索、MCP 和配置工具，从入口追踪直接依赖：

1. 确定业务触发入口、关联请求/应答/通知及可观察结果。
2. 从条件判断找必要配置和状态，不预先加载整个系统配置。
3. 查找现有业务操作、GM、LocalLogic 或 Block 以准备条件，核对真实参数。
4. 确定准备后的状态核验方式及被测操作的事前预期依据。
5. 用原有 Block 格式编排，执行并保留必要证据。

资料只提供定位和候选操作；当前协议从实际 MCP 核对，实际配置从测试环境读取，角色条件实时查询。识别本地源码、benchmark 与游戏服务部署版本差异，无法核实时标记未知，不把本地 Git 版本冒充部署版本。

## 收尾：只保存复用增量，不默认写测试报告

测试结果与报告规则见主 Skill。本页只规范可复用能力资料：入口、准备操作、适用条件及最小验证证据；不在此重复测试报告政策。客户端本地 Run 清单及脱敏原始响应用于续读，见 client.md。

先判断是否有值得复用的增量：新入口、实际验证过的准备路径、原资料纠错或适用条件变化。已有资料仍适用且没有新增信息时不写文档、不为本次重复运行刷新日期，也不重新生成报告。首次确有复用增量时用一份精简笔记；需要跨功能复用时再拆能力。按具体结论标记状态，不将整篇笔记统一标为“已验证”。

最小记录如下，采用自然语言 Markdown，不增加执行器格式；已有内容只补变化的条目：

```text
功能/能力与领域：名称、别名或领域标签
入口与来源：路径、符号及相关版本依据
准备及核验：必要操作、参数来源、完成检查
适用条件：依赖、限制及必要的副作用说明
验证状态与证据：未验证/已验证/失效，实际环境、Run ID/步骤及证据位置
```

来源只记录支撑复用的相关文件内容哈希或其他可核查版本依据，包括未提交修改；未知部署版本明确未知。不为填模板额外扫描整个仓库。预期依据、争议、缺口仅在影响复用或解释结果时补充，不复制完整协议、配置、Trace 或整段分析过程。

保存失败时如实说明未保存；不承诺回合结束后后台继续沉淀。

“已验证”必须能说明具体条件下实际执行了哪一步、用什么检查确认了哪个结果。单纯 status=succeeded、无报错、准备命令返回成功，均不能证明角色已满足业务前置条件。部分流程失败不妨碍单独记录已有充分证据的准备步骤；未到达的步骤不升级验证状态。

首次建立资料目录时创建 `00-索引.md`；若该目录位于 Obsidian 的 `AI工具链/` 下，再在对应上级索引添加一次入口。后续仅在入口新增、链接/分类变更或失效时更新必要索引；正文补充和重复测试不动索引，不同时维护重复导航。遵守 vault 文件权限，先准备可审阅内容，再通过所需权限写入；不得把未写成功说成已保存。

长期笔记只保留经筛选的核验事实与证据定位，不复制登录令牌、账号密码、连接凭据或全量玩家存档。需要长期保留的 Block 片段沿用原格式并移除角色专属值和凭据，参数来源写清楚；参数化后的片段属于新候选，未经执行不能继承旧实例的已验证状态。原始响应留在私有证据目录；临时文件将来可能不存在，缺失时该验证记录只能作为历史线索，必要时重新取证。

## 下次：局部核查，不盲目复用

- 相关文件哈希不变，仅说明这些来源未变；仍需确认运行环境、配置和当前角色状态。分支名或 commit 相同不足以排除本地未提交修改。
- 公共能力变化时沿案例中的依赖链接复核受影响组合；旧案例不自动继承新能力的验证结果。
- 来源变化时，重新读变更及受影响依赖，重新核实相关结论后更新记录。依赖图并非完整时，不能只比较入口文件就认定安全。
- 配置记录保存表/字段及查询方式；旧值只能作为当次快照。协议记录保存关联与来源；旧字段不能直接作为当前调用契约。
- 已有 Block 先读当前版本和前置条件。资料沉淀本身不触发 commit_block_draft；实际组合需要新子 Block 时按本次授权保存独立 ID 并确认可加载，不覆盖已有共享 Block。缺少持久 Block 时由 Agent 从资料生成原生草稿，不要求用户手写；具体保存与组合规则见 client.md 的 Block 编写流程。
- 遇到反证时将受影响结论标为失效，保留简短原因及旧验证范围，避免下次继续命中错误结论。不得为了让测试通过修改历史预期依据。

不要求第一次测试更快，也不把首次探索耗时归为工具失败。评估优化时分别统计首次发现、重复测试及资料维护耗时，结合工具调用/回传量和准备中断次数；复用收益必须计入维护成本。日常测试沿用已有计时数据，不为统计另写多份台账；没有模型计量则不填推测 token 数。
