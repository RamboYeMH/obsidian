奖励可达性 & 重复领取分析

核心数学不变量

TtlScr = 终身累计积分（只增不减）；Score = 当前可用积分；limit = 每次循环所需积分；ReopenScoreMap[k] = key k 已领到的 totalCnt 值。

每次成功领奖后：Score -= cnt * limit（cnt = Score / limit），
领奖后 Score = Score % limit < limit，因此 cnt = 0。

当下次新积分到来（+delta）：
keyCnt = ((R + delta) / limit)，cnt = ((R + delta) / limit)， keyCnt ≡ cnt 始终成立，Score -= cnt * limit 永远精确对应实际发放量。

下次领奖时的计算
// key=0：ReopenScoreMap[0] = N，keyCnt = totalCnt - N（仅新增）
// key=1：ReopenScoreMap[1] = 0，keyCnt = totalCnt（全历史追领）
cnt = Score / limit = R / limit = 0   // 余数 R < limit

key=1 获得了 totalCnt 次奖励，但 Score 没有减少。这是现有架构的固有行为，不是 1042 修复引入的问题，但可能属于未预期的"追领免费"现象。 建议与策划确认：购买付费档是否应补发历史循环奖励，以及是否应消耗对应 Score。

backfill 公式正确性证明

证明：claimedCnt = totalCnt − cnt 精确还原已领次数

设最近一次领奖时 TtlScr₀，levelUpCost 不变，claimed 为真实已领次数。

领奖后：Score_after = (TtlScr₀ - levelUpCost) % limit（不变量）

领奖后到服务重启期间积累 Δ 分：TtlScr = TtlScr₀ + Δ，Score = Score_after + Δ

backfill 时：
totalCnt = (TtlScr₀ + Δ − levelUpCost) / limit
= (claimed·limit + Score_after + Δ) / limit
= claimed + (Score_after + Δ) / limit

cnt = Score / limit = (Score_after + Δ) / limit

∴ claimedCnt = totalCnt − cnt = claimed　Q.E.D.

该等式对任意 Δ（领奖后的额外积分）成立，即 backfill 公式与领奖后到服务重启之间积累了多少积分无关，始终精确。

场景 C
cnt ≡ keyCnt 恒等式——Score 扣减始终精确
证明任意领奖时刻 Score -= cnt * limit 与实际发放量严格对应

设上次领奖时已领次数为 P（ReopenScoreMap[k] = P），领奖后 Score 为余数 R = Score % limit < limit。

之后玩家积累 Δ 分（TtlScr += Δ，Score = R + Δ）：

推导
totalCnt = (TtlScr − levelUpCost) / limit
         = (P·limit + R + Δ) / limit
         = P + (R + Δ) / limit

keyCnt   = totalCnt − P  =  (R + Δ) / limit

cnt      = Score / limit  =  (R + Δ) / limit

∴  keyCnt ≡ cnt  （对任意 R、Δ 均成立）
无论上次领奖距现在积累了多少分，Score -= cnt * limit 扣减的都是 本次实际发放的循环数对应的积分，不多扣也不少扣。
场景 D
手动领奖 RPC 与活动结算 sendRewardsAll 的幂等性
两条路径共享同一 ReopenScoreMap，任意先后顺序均不重复发放
情况 1：手动领奖先于结算
① ctl.go  → SetReopenScore(k, totalCnt)  → ReopenScoreMap[k] = T
② logic.go → keyCnt = T − T = 0  → 跳过，不再发放
情况 2：结算先于手动领奖
① logic.go → ReopenScoreMap[k] = totalCnt（直接写，功能等价）
② ctl.go   → GetReopenScore(k) = T，keyCnt = T − T = 0  → 跳过
Activity 模块基于 chanrpc 单线程执行，两条路径天然互斥，不存在并发竞争。 无论哪条路径先完成，后续路径看到的 keyCnt = 0，奖励不重复发放。
注意：logic.go 的直接写 ReopenScoreMap[k] = totalCnt 属于遗漏项（见 P1 待修复）， 当前不会 panic 是因为同循环体内 GetReopenScore(k) 已先初始化 nil map， 功能逻辑正确但存在执行顺序依赖的隐患。
场景 E
批量加载架构保证时序安全
actv 模块启动时全量加载，backfill 在任何领奖请求前完成

actv 模块通过 loadProgress 在启动时分页（500条/次）批量加载所有活动进度数据到内存。 全部加载完成后统一派发 IEventAfterLoaded，触发 RangeProgress 遍历所有玩家执行 backfill。

chanrpc 模块收发消息是单线程的，玩家的领奖请求必须等待 actv 模块启动完成后才能被处理， 因此 backfill 在任何领奖请求到达之前已全部完成，不存在"数据已加载但 backfill 未运行"的时间窗口。

启动顺序
loadProgress（批量加载所有玩家进度）
  ↓
IEventAfterLoaded 派发
  ↓
onAfterLoadedEvent → RangeProgress → backfillReopenScoreMap（所有玩家）
  ↓
actv 模块进入正常服务状态
  ↓
玩家领奖请求开始被处理
不存在老玩家"绕过 backfill 直接领奖"导致重复发放的路径。
场景 F
新购档位（DataMap 新增 key）后领奖——零 Score 成本追领
设计层面的正确性存疑，与 1042 修复无关

玩家使用 key=0 领了 N 次（Score 已被扣减至余数 R < limit），随后购买 key=1，触发领奖：

具体计算
// 购买后 Score = R，TtlScr 未变
totalCnt        = (TtlScr − levelUpCost) / limit = N（假设无新积分）
ReopenScoreMap[0] = N   → keyCnt[0] = 0（已全部领完）
ReopenScoreMap[1] = 0   → keyCnt[1] = N（全历史追领）

cnt   = R / limit = 0   （R < limit）
Score -= 0 * limit = 0  → Score 无减少，但 key=1 获得了 N 次奖励

这是原有架构的固有行为（新档位购买即补领历史），不是 1042 修复引入的变化。 但零 Score 成本获得 N 次奖励可能不符合策划预期，属于设计层面待确认项（见 P2 待修复清单）。
