设计
类型断言：硬编码具体类型 → 类型参数断言
utility/pbutil.go · CopyProtoMap
design

改前

  • 具体类型硬编码在断言处
  • 传错类型编译通过，运行时 panic
  • 每种消息类型需单独写一个循环
  • 类型正确性由调用方自律保证

改后

  • 具体类型由类型推断自动填入
  • 约束不满足编译直接报错
  • 任意 map[K]proto.Message 复用同一函数
  • 类型正确性由编译器强制保证
改前 — 硬编码类型断言
cloned := make(map[int64]*cspb.LeagueWarLeagueInfo, len(src))
for uid, info := range src {
    cloned[uid] = proto.Clone(info).(*cspb.LeagueWarLeagueInfo)
    // 传入其他消息类型 → 编译通过 → 运行时 panic
}
改后 — 泛型约束 + 类型推断
func CopyProtoMap[K comparable, V proto.Message](src map[K]V) map[K]V {
    dst := make(map[K]V, len(src))
    for k, v := range src {
        dst[k] = proto.Clone(v).(V)  // V 由调用方类型推断保证，断言安全
    }
    return dst
}

// 调用方：K=int64, V=*cspb.LeagueWarLeagueInfo 自动推断
utility.CopyProtoMap(d.Groups[zvzGroupId])
设计
Go 类型推断：从实参反推类型参数
Go 1.18 · Type Inference
design

调用 utility.CopyProtoMap(d.Groups[zvzGroupId]) 时，编译器从实参类型 map[int64]*cspb.LeagueWarLeagueInfo 自动推断出 K = int64、V = *cspb.LeagueWarLeagueInfo，随即做两项约束检查：

编译期约束验证过程
// Step 1：从实参类型推断类型参数
K = int64                          // ← 从 map key 类型推断
V = *cspb.LeagueWarLeagueInfo      // ← 从 map value 类型推断

// Step 2：验证约束
int64 satisfies comparable         // ✓ map key 本就要求 comparable
*LeagueWarLeagueInfo satisfies     // ✓ 实现了 Reset() String() ProtoMessage()
  proto.Message

// 若约束不满足：编译报错，不到运行时
utility.CopyProtoMap(map[int64]string{})  // compile error: string 不满足 proto.Message
设计
.(V) 仍是运行时断言，但安全性来源已改变
GC Shape Stenciling · 类型参数上的类型断言
design

proto.Clone(v).(V) 在技术层面仍是运行时类型断言，Go 的类型系统无法静态证明 proto.Clone 的返回值是 V。两种写法的安全性来源不同：

两种断言的安全性对比
// 改前：安全性依赖"调用方碰巧传对了类型"
proto.Clone(info).(*cspb.LeagueWarLeagueInfo)
// 错误类型传入 → 编译通过 → 运行时 panic
// 安全性保证：调用方自律，文档说明，没有任何强制

// 改后：安全性由"类型推断 + proto.Clone 契约"双重保证
proto.Clone(v).(V)
// V 由类型推断从 map value 类型确定（编译期）
// proto.Clone 保证返回与输入相同的具体类型（API 契约）
// 两者结合 → .(V) 在运行时永远不会失败
这是 Go 泛型与 C++ 模板的重要区别：Go 泛型约束描述接口行为，不描述具体结构，涉及接口函数返回值时仍需运行时断言。安全性的提升来自"把类型绑定的责任从调用方转移给类型系统"，而非消除断言本身。

运行时开销方面：*cspb.LeagueWarLeagueInfo 是指针类型，Go 编译器通过 GC Shape Stenciling 让所有 map[K]*proto.Message 实例共享同一份机器码，额外开销仅一次间接寻址，与手写循环等价。

设计
proto 依赖收敛：从散落业务包到 pbutil 单点管理
utility/pbutil.go · import 隔离
style

改前 holddata 包直接 import proto 只为 proto.Clone 一行调用；改后移除该 import，proto 操作集中在 utility/pbutil.go。

改前 — holddata 直接依赖 proto
import "github.com/gogo/protobuf/proto"
// holddata 包因一行 Clone 调用引入重型依赖
改后 — proto 依赖收敛到 pbutil
// utility/pbutil.go — proto 依赖的唯一入口
import "github.com/gogo/protobuf/proto"

// holddata/leaguewar_union_info.go — 不再直接依赖 proto
import "git.tap4fun.com/k3x/gs/utility"
后续新增 proto 拷贝需求，统一调用 utility.CopyProtoMap，不需要在各业务包分别引入 proto 依赖。

设计亮点

  • 约束选型精准：K comparable 与 Go map key 要求完全对应，V proto.Message 精确描述了"可被 proto.Clone 处理"的语义，约束既不过宽也不过窄。
  • proto 依赖隔离：新建独立文件 pbutil.go 承载 proto 依赖，utility 包其余文件保持零 proto 依赖，职责边界清晰。
  • 调用方零感知：类型推断使调用方无需写类型参数，与手写循环的调用复杂度相当，迁移成本极低。
  • 可复用性：函数对 K/V 类型无具体约束，项目中任意 map[K]*SomeProtoMsg 的深拷贝均可直接复用，无需为每种消息类型单独实现。
