⚠ 根因结论

代码使用 onlineCfg.ContentID 作为任务配置的唯一查找键（GetQuestCfgsByContentID）， 该函数对配置表做全表扫描，无活动维度隔离。当新活动 B 复用了旧活动 A 的 ContentID，且旧活动 A 的任务配置仍保留在表中， 新活动初始化时会将旧任务（T_A*）与新任务（T_B*）一并写入玩家进度。 玩家在新活动期间触发旧任务的完成条件，活动结束时 SendEndMail 调用 GetActvQuestCfg(旧TaskId) 可以正常找到旧配置， 从而把旧活动的奖励（如 T_A* 对应的 Reward）随新活动的结算邮件一起发出，造成玩家收到本不属于当前活动的奖励， 破坏游戏经济平衡。此路径全程无错误日志，属于静默数据污染。

触发条件：策划复用 ContentID 且未清理旧任务配置；根本缺陷：任务加载无活动隔离，代码对「ContentID 唯一性」无任何约束； 扩大因素：checkAndAddNewTasks 只增不减，旧任务 ID 一旦写入玩家进度永不移除。

触发链路

现象描述

BUG
活动结束结算邮件中混入旧活动的奖励
wish_pool_v2/logic.go · SendEndMail

活动 B 正常结束，OnEnd 触发 SendEndMail。玩家收到的结算邮件中包含了不属于当前活动 B 的奖励物品（与旧活动 A 的任务奖励相同）。 服务端全程无错误日志产生，代码逻辑正常执行，属于静默数据污染。

客户端表现：玩家发现邮件奖励与当期活动公告不符，收到的物品/数量超出预期，或包含历史活动才有的道具。

与「奖励丢失」不同：此 BUG 是多发了不该发的奖励，且没有 nil 报错作为报警信号，只能通过发奖 BI 日志与配置对比才能发现。

复现步骤

  1. 配置活动 A（CfgID=100，ContentID=50），任务表中 ContentId=50 对应任务 T1/T2/T3，奖励分别为 R_A1/R_A2/R_A3（旧活动专属物品）。
  2. 活动 A 正常运行并结束，玩家 prg 已清结。
  3. 策划配置活动 B（CfgID=200，复用 ContentID=50），在任务表为 ContentId=50 新增任务 T4/T5/T6，奖励为 R_B4/R_B5/R_B6（新活动物品）。旧任务 T1/T2/T3 未从配置表删除，仍挂在 ContentId=50 下。
  4. 活动 B 开启，玩家登录，触发 QuestPackProto。
  5. initTask 调用 GetQuestCfgsByContentID(50)，全表扫描返回 T1/T2/T3/T4/T5/T6 共 6 条，全部写入玩家 TaskInfos。
  6. 玩家在活动 B 期间进行正常游戏，老任务 T1/T2/T3 的完成条件（如累计抽卡次数等）被同样触发，状态变为 QuestStateFinish。
  7. 活动 B 结束，SendEndMail 遍历玩家 TaskInfos，T1/T2/T3 状态为 Finish，调用 GetActvQuestCfg(T1) 返回有效配置，R_A1/R_A2/R_A3 被发出。
  8. 玩家结算邮件中同时包含 R_B4/R_B5/R_B6（正确）与 R_A1/R_A2/R_A3（旧活动奖励，不该发），全程无错误日志。
此路径不产生任何 nil 报错，BI 发奖日志量正常，仅对比发奖物品与活动配置才能发现异常。

根因分析

触发条件
策划为新活动复用了旧活动的 ContentID。
ActvOnlineCfg.ContentID 被设计为一个「内容模板标识」，可被多期活动引用（如排行榜、奖池配置均以 ContentID 作为 key）。但在任务配置层面，ContentID 被用作唯一聚合键，一旦复用，新旧任务数据混在同一 ContentID 下，代码无法区分。
根因
任务加载无活动维度隔离，代码对「ContentID 唯一性」无任何约束保证。
GetQuestCfgsByContentID（conf_actvquest_ext.go:41）对 ActvQuestCfg 表做全表扫描， 只要 ContentId == X 就返回，不关心该任务属于哪一期活动（无 CfgID 过滤）。 initTask 和 checkAndAddNewTasks 盲目信任此返回值，将所有 ContentID=X 的任务一并写入玩家进度， 老任务（T_A*）与新任务（T_B*）混在同一个 TaskInfos 中无法区分。

SendEndMail 遍历 TaskInfos 时，对状态为 QuestStateFinish 的任务均调用 GetActvQuestCfg(taskId) 查奖励配置并发出——旧任务 T_A* 有有效配置、完成条件也可被触发， 因此旧活动的奖励（R_A*）被合法地随新活动结算邮件发出，全程无报错，属于逻辑正确但语义错误。
扩大因
checkAndAddNewTasks 只增不减，孤儿任务永远留在玩家进度中。
该函数逻辑：遍历 questMap，若 taskId 不在玩家现有 TaskInfos 中则追加。但反过来——玩家 TaskInfos 中已有的 taskId 如果不在 questMap 中，不会被清除。 一旦配置热更删除某任务，其 ID 在玩家进度中永久残留，每次 QuestPackProto 都会触发 nil 日志， SendEndMail 也会对其静默丢奖。

影响范围

直接受影响：在活动 B 存续期间登录过的所有玩家，其 TaskInfos 中含有旧任务 T_A*，且在活动 B 期间触发了旧任务完成条件。

数据异常：玩家额外收到旧活动的奖励（R_A*），游戏经济被注水。奖励已发出，状态已推进到 QuestStateReward，无法仅通过状态回滚修复，需人工核查发奖日志追回。

服务稳定性：不影响服务进程，无崩溃/报警。

可发现性：无错误日志，监控无异常。只有玩家主动举报或策划主动对比 BI 发奖数据时才会暴露，发现成本高。

此 BUG 属于静默数据污染，危害程度高于产生报错的 BUG，因为后者至少可以被监控感知。

  5. 验证方案 C（孤儿清理）：令玩家在旧配置存在时先登录（prg 写入旧任务），再热更删除旧任务，再次登录后确认孤儿 ID 被从 TaskInfos 清除。

延伸风险

  • 同类模板风险：christmas_tree、lost_mine 等其他使用 ContentID 加载任务的活动模板存在相同缺陷，建议全面排查历史活动 ContentID 是否有复用情况，核查对应发奖记录。
  • 奖励丢失次生风险：若旧任务配置在活动 B 运行期间被删除（热更清理），此前已写入玩家 prg 的旧 ID 将触发 GetActvQuestCfg 返回 nil，从而变成「奖励丢失」场景。两种场景的触发取决于旧配置是否删除，实质根因相同。
  • 可观测性缺口：此类静默多发的监控缺失。建议在 SendEndMail 中对发出奖励的 questId 做 questMap 归属校验，对不在 questMap 内的任务发奖行为打告警日志，提升可发现性。
  • 配置管理规范：建议在活动配置工具侧增加 ContentID 唯一性检测，或在 GetActvOnlineCfgExt 加载时扫描 ContentID 冲突并打 Warning，从数据源头拦截。
