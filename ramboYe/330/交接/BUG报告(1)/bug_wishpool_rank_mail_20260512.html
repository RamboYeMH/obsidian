3

Redis 脏数据污染（核心根因）

☣️
核心结论：wish_pool_v2 当前代码从不写 Redis，GetRankKey()="" 本意是让 settleRankReward() 查询空 key 从而得到空结果、实现"软禁用"。但测试环境 Redis 残留 key="" 的脏数据，导致废弃路径被意外激活，触发重复发奖。

3.1 wish_pool_v2 从不向 Redis 写入排行数据

wish_pool_v2 在更新排行分时走的是本地 RankPlay.Update()，完全不经过 Service.UpdateRankScore()，因此 Redis 排行服中不会产生任何来自本活动的当次数据：

// wish_pool_v2/ctl.go — updateRankScore（玩家每次许愿后调用）
func (a *ActvTmplWishPool) updateRankScore(sid int32, playerID int64, val int64, meta string) {
    // 本地写入：RankPlay（in-memory + MongoDB）
    a.RankPlay.Update(a.createRankKey(rankStageServer, sid), playerID, val, meta)
    a.RankPlay.Update(a.createRankKey(rankStageGroup,  sid), playerID, val, meta)

    // ↓ 以下代码从未被调用 → Redis 中无 wish_pool_v2 的当次排行数据
    // a.Service.UpdateRankScore(a, pc, typ, score, add, meta)
    // → 若调用则会 Cast(RANK, &UpdateRankNodeReq{RankId: GetRankKey()="", ...})
}

3.2 GetRankKey() 返回 "" 作为"软禁用"开关

GetRankKey() 是 settleRankReward() 查询 Redis 所用 key 的来源。wish_pool_v2 没有实现此方法，直接返回空字符串 ""。设计意图是：key="" 对应 Redis 中的空排行，GetRank 返回空数组，settle() 不执行任何操作——相当于软禁用废弃路径：

// wish_pool_v2/api.go:163 — 未实现，返回 "" 作为"禁用"开关
func (a *ActvTmplWishPool) GetRankKey(typ cspb.RankType, pc *mcache.ActvPlayerCache) string {
    tlog.Warnf("actv:%v GetRankKey need override typ:%v", a.ActvBrief.CfgID, typ)
    return ""  // ← 预期效果：Redis key="" 应为空，settle() 不执行
}

// actv/cactv/internal/service.go:214 — GetRank 流程

    rankKey := actv.GetRankKey(typ, cache)  // ← rankKey = ""
    common.SendRankReqByPage(a, &cspb.GetRankListReq{
        RankId: rankKey,  // ← 查询 Redis key=""

// actv/main.go:140 — rankmgr 是进程内 Redis 排行服
rankmgr.NewRankMgr(conf.RedisHost, conf.RedisPasswd)

⚠️
软禁用的致命前提：Redis key="" 必须始终为空 这一机制依赖于 Redis 中 key="" 不存在任何数据。只要测试环境 Redis 未被清理，或曾经以旧版本代码（调用过 UpdateRankScore）运行过，key="" 就会有残留数据，软禁用立即失效。

// wish_pool_v2/logic.go:88-116 — settleRankReward() 完整流程
func (ths *ActvTmplWishPool) settleRankReward() {
    actvProgress := ths.CoreComp.GetProgress()
    if actvProgress.RankSettle {
        return
    }
    defer func() {
        actvProgress.RankSettle = true  // ← defer：函数 return 后立即设置，早于异步回调
        actvProgress.MakeDirty()
    }()

    // 服排循环：按每个 sid 查询 Redis key="" → 取回脏数据
    for sid := range actvProgress.Servers {
        sid0 := sid
        ths.Service.GetRank(ths, &mcache.ActvPlayerCache{GameServerID: sid},
            cspb.RankTypeCrossActvWishPool, 0, findMaxRank(rankSecCfgs),
            func(rankPbs []*cspb.RankItem, self *cspb.RankItem) {
                ths.settle(..., rankPbs, sid0, 0)  // ← 脏数据触发发奖
            })
    }

    // 组排循环：同上，对每个 group 查 Redis key=""
    for group, sids := range actvProgress.Groups {
        group0 := group
        ths.Service.GetRank(ths, &mcache.ActvPlayerCache{GameServerID: sids[0]},
            cspb.RankTypeCrossActvWishPoolGroup, 0, findMaxRank(groupRankSecCfgs),
            func(rankPbs []*cspb.RankItem, self *cspb.RankItem) {
                ths.settle(..., rankPbs, 0, group0)  // ← 脏数据触发发奖
            })
    }
}

// wish_pool_v2/logic.go:117-160 — settle() 路由逻辑
func (ths *ActvTmplWishPool) settle(..., sid int32, group int32) {
    for _, item := range rankItems {
        ...
        playerSid := sid
        if playerSid == 0 {
            // 组排行路径：从 PlayerComp 读 Sid 决定路由目标游戏服

        }
    }
}

4.3 事件时序还原

0
前置：测试环境 Redis 存在脏数据 Redis key="" 保有来自上次测试或旧版本代码的排行数据，包含玩家 A、B 的真实 PlayerID 与排名。wish_pool_v2 本次运行从未向 Redis 写入数据，脏数据完全来自历史残留。
1
OnEnd() 触发，系统一正常发奖 sendRankRewards() 读取本地 RankPlay 数据，经 GroupByServerId 分服路由：A(ServerID=S1) → GS1，B(ServerID=S2) → GS2。游戏服两端均经过 OriginServerID 校验，A 正确收到第2名邮件，B 正确收到第189名邮件。
2
系统二（废弃路径）从 Redis 取回脏数据 settleRankReward() 调用 Service.GetRank(key="")，Redis 返回了包含 B.ID(rank=189) 的脏排行列表。defer RankSettle=true 在函数返回时执行，此时异步回调尚未触发。
3
settle() 用 account.Sid 路由，指向 S1 组排行路径：settle(rankItems=[B:189,...], sid=0) → PlayerComp.GetProgress(B.ID).Sid，取到 B 的账号记录中的 Sid（可能是 S1 或 S2，具体取决于账号初始化时的值）。若 Sid=S1，则 ClusterCastToGameServer(S1, msg.PlayerID=B)。
4
游戏服 S1 无校验直接发邮件 onS2SA2GActvMailSendReq 收到 PlayerID=B, rank=189 的消息，没有 OriginServerID 校验，直接调用 SendSysTextMail(B.ID, ...)。若 S1 上 B.ID 对应 A 的角色（PlayerID 碰撞）或测试人员以 A 账号登录时 B 的邮件出现在同服邮箱，A 额外收到「第189名」邮件。

修复方案

P0
从 OnEnd() 中删除 settleRankReward() 调用 wish_pool_v2 已通过本地 RankPlay 完整管理排行数据，settleRankReward() 是历史遗留的废弃路径，只要测试或生产 Redis 中 key="" 有任何数据就会误触发。最简修复：直接删除 OnEnd() 中对 settleRankReward() 的调用，同时可将 settleRankReward() 整体删除或以 //Deprecated 标注。
P0
onS2SA2GActvMailSendReq 增加 OriginServerID 校验 参照 OnA2PPendPlayerMails 的逻辑，在 onS2SA2GActvMailSendReq 中对每个 PlayerID 校验 pc.GetOriginServerID() == conf.ServerID，不通过则跳过并打 Warn 日志，从根本上堵住跨服错投通道。
P1
settle() 中增加 account.Sid 合法性校验 取到 account.Sid 后，验证其是否存在于 actvProgress.Servers 合法服务器列表中，不在则跳过并打 Warn 日志，防止异常 Sid 路由到随机游戏服。
P1
修复 defer 竞态：RankSettle 标记移到所有回调完成后 使用计数器或 sync.WaitGroup 追踪所有 GetRank 回调的完成情况，全部完成后再将 RankSettle=true 持久化，避免进程崩溃时邮件永久丢失的问题（此项仅在保留系统二的情况下需要处理）。
P2
测试环境 Redis 清理规范 多服数据合并导入前，须清理 Redis 中所有排行相关 key（尤其是 key=""），或在测试脚本中增加 Redis 数据重置步骤，防止脏数据激活任何废弃路径。
