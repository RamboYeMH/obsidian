# 测试用例：洞穴生命周期不一致导致无法创建新洞穴

## 测试目标

验证 actv 的 `packProto` 和 wmap 的 `timerLostMineTicker` 对洞穴生命周期判断不一致时，玩家创建新洞穴被拦截的问题。

## 前置条件

| 条件 | 说明 |
|------|------|
| 测试环境 | h5dev 任意环境 |
| 配置修改 | `AdventureBuildCfg.tsv` 中目标洞穴的 `DestoryTime` 改为 60（1分钟） |
| 账号要求 | 有联盟的玩家，城堡在地图上 |
| 配置重建 | `make conf` 后重启服务 |

---

## 用例 1：部队在洞穴内 + deadline 到期 → 新洞穴创建被拦截

| 步骤  | 操作                           | 预期结果                                                                    |
| --- | ---------------------------- | ----------------------------------------------------------------------- |
| 1   | 打开"洞穴历险"活动                   | 正常展示 3 个洞穴 slot                                                         |
| 2   | 刷出一个 4★ 洞穴（或直接用初始 slot 中的洞穴） | 洞穴信息正常显示                                                                |
| 3   | 点击"探索"，将洞穴放到地图上              | 地图上出现洞穴建筑，活动内该 slot 状态变为"存在中"                                           |
| 4   | 派一支部队行军进入该洞穴                 | 部队进入洞穴，开始探索                                                             |
| 5   | 等待 DestoryTime 到期（60s）       | —                                                                       |
| 6   | 重新登录或关闭再打开"洞穴历险"活动           | 触发 `packProto`，该 slot 状态变为"已坍塌"（Crashed）                                |
| 7   | 观察地图上的洞穴是否还存在                | **地图上洞穴仍然存在**（因部队未退出，wmap timer 不删除）                                    |
| 8   | 点击另一个 slot 的洞穴（如 5★），点击"探索"  | **预期 BUG 现象**：返回 `ErrCodeLostMineCanExistOnlyOne`，客户端无反应或错误提示不明确        |
| 9   | 检查服务端日志（修复日志后）               | wmap 返回 `ErrCodeLostMineCanExistOnlyOne`，原因：Creator 仍有关联的 LostMine unit |

## 用例 2：部队全部退出 + deadline 到期 → 正常创建新洞穴（对照组）

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 重复用例 1 的步骤 1-4 | 洞穴在地图上，部队在洞穴内 |
| 2 | 等待 DestoryTime 到期（60s） | — |
| 3 | **召回部队**（让部队退出洞穴） | 部队离开洞穴 |
| 4 | 等待 timer 周期触发（约 1-2 tick） | wmap `timerLostMineTicker` 检查 `troops==0 && now>deadline`，删除洞穴 |
| 5 | 重新登录或打开"洞穴历险"活动 | 该 slot 变为"已坍塌" |
| 6 | 点击另一个 slot 的 5★ 洞穴，点击"探索" | **正常**：成功创建新洞穴，返回 `ErrCodeSuccess` |

## 用例 3：deadline 未到期 + 部队在洞穴内 → 不能创建新洞穴（正常行为）

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 创建洞穴，部队进入 | state=Exist |
| 2 | 在 deadline 未到期时，尝试创建另一个洞穴 | **预期**：actv 侧直接拦截，返回 `ErrCodeLostMineCanExistOnlyOne` |
| 3 | 客户端表现 | 应有明确的错误提示（如"已有洞穴存在"） |

## 用例 4：不同星级洞穴的 deadline 差异

| 洞穴 | cfgid | DestoryTime(原) | DestoryTime(测试) |
|------|-------|-----------------|-------------------|
| 1★ | 4001 | 8000s | 60s |
| 2★ | 4002 | 12000s | 60s |
| 3★ | 4003 | 16200s | 60s |
| 4★ | 4004 | 26400s | 60s |
| 5★ | 4005 | 43200s | 60s |

> 测试时统一改为 60s，验证所有星级洞穴均存在相同问题。

## 用例 5：修复后回归验证

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 重复用例 1 的步骤 1-6 | deadline 到期，packProto 触发 |
| 2 | 观察地图 | **修复后预期**：洞穴被正确删除（部队被强制召回），或 actv 侧 state 保持 Exist 直到 wmap 删除 |
| 3 | 尝试创建新洞穴 | **预期**：创建成功 |

## 测试数据检查点

MongoDB 查询验证（`game<实例>.actvprogress`）：

```javascript
// 查询玩家洞穴进度
db.actvprogress.findOne({ownerid: <玩家ID>, actvid: <活动ID>})

// 检查 mines 数组中各 slot 的字段：
// - state: 0=None, 1=Exist, 2=Crashed
// - entityid: 0 表示无地图实体关联
// - deadline: 0 表示已过期/未设置
// - coord: {x:0, z:0} 表示坐标已清除
```

| 阶段 | state | entityid | deadline | 说明 |
|------|-------|----------|----------|------|
| 创建前 | 0 (None) | 0 | 0 | 未创建 |
| 创建后 | 1 (Exist) | ≠0 | ≠0 | 地图上有实体 |
| deadline到期+packProto | 2 (Crashed) | 0 | 0 | actv 已清除 |
| 修复后预期 | 2 (Crashed) 或 1→实体已删 | 0→实体删 | 0 | 与 wmap 一致 |
