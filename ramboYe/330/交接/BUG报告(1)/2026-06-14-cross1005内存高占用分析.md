## 冰剧本对内存的具体贡献

### 贡献1：5月活动 28,834 条 PlayerCache 从未清理（最主要）

实例 7638278072650610125（actType=154, 9服）自 **2026-05-04 启动，运行超5周**，`deletedmap=0` → `DelByTimeOut` 从未被调用：

```
9服 × ~3,200玩家 = 28,800条 ≈ 实测 28,834 完全吻合
```

### 贡献2：v1044 actType=155 参战服从 9 扩至 12（+33% 规模）

3个12服分组（group 3000/3001/3005）额外引入约 +6,300 条 PlayerCache。

### 贡献3：最老地图冰霜怪异常积累（3,966 vs ~1,941）

- 5周老图 vs 新图：NPC 数量约 **2 倍差距（3966 vs 1941）**
- 差值 ~1,700 个 NPC 疑因 v1044 bug（`280d6adcfb`：冰霜怪驻防人数计算错误，把工厂驻防也计入阵营中心）→ `GarrisonCount` 虚高 → 触发更高级别 IceFrostMonsterCfg → 可能触发多余刷怪，老图积累未清理

### 贡献4：v1045 融冰编队自动回城增加行军单位密度

```go
// ef6e8f8e11: ctl_battlefield_melting_ice.go
wmap.RecallTroop(troop)  // 融冰完成后自动行军回城
```

行军单位增多 → `ObMgr.GetMarchingUnits` 追踪量增大 → 对应 pprof 中 5.58% cum。

### 贡献5：冰髓战战斗阶段全量遍历 14,050 NPC（CPU→GC→内存）

每帧 `RangeUnits → exitBattleLogic → RangeBattleUnit → IsDead() → SumMapValueByCond(SoldiersInfo)` 对所有 NPC 遍历，对应 pprof 中 `IsDead 8.23s cum (11.54%)`，大量临时对象触发 GC，抬高 heap 水位。

## 应急处理

1. **立即**：GM 触发 `DelByTimeOut` 清理 >7天 PlayerCache（预计释放 ~400MB+）
2. **6/16 冰髓战结束后**：确认老图 3,966 个 NPC 是否随活动结束被正确清理
3. **长期**：cross server 加独立定时 PlayerCache 清理逻辑，不依赖地图删除

## 关键发现

### GC 开销极高（间接内存信号）

GC 相关函数累计占 CPU **40%+**：

| 函数 | flat | cum |
|------|------|-----|
| `runtime.findObject` | 10.49% | 11.44% |
| `runtime.scanobject` | 2.33% | 15.98% |
| `runtime.gcDrain` | 0.31% | 16.46% |
| `gcWriteBarrier` | 0.59% | 5.66% |
| `runtime.wbBufFlush1` | 0.50% | 5.83% |

结论：**heap 对象数量和体积极大**，GC 频繁、耗时扫描。

## 根因排序

### 根因 1：PlayerCache 大量常驻内存 ⭐ 最主要

**路径**：`cross/play/internal/handler.go:33` → `cache.PCD.Put(c)`

每当各游戏服发来 `SyncPlayerCacheReq`，都往 `PlayerCacheMgr.Players`（`sync.Map`）写入记录。Cross server 从所有参战服同步，**全部常驻内存，无日常清理**。

清理时机极滞后：
```go
// game/wmap/duplicatemgr/duplicatemgr.go:35
DUPLICATE_TIEMOUT_DEL = 7  // 7天后随地图删除才清理
```

`PlayerCache` 结构体极重（50+ 字段）：
- `Props map[int32]float64`
- `TechLevel map[int32]int32`
- `WitchRunne map[int32]int32`
- `TrialTowerLastTime map[string]int64`
- `Counter *count.Counter`（含内部 map）
- `DefenseCampCache *DefenseCampCache`（含 `map[int64]*DefenseHero`）

**估算**：5000 名玩家 × ~15-20KB ≈ **75-100MB** 仅 PlayerCache 就消耗。

---

### 根因 2：sync.Map 装箱放大 GC 扫描

`PlayerCacheMgr.Players` 是 `sync.Map`，底层 `HashTrieMap[interface{},interface{}]`：
- 每个 entry 都是 interface{} 包装，带指针
- GC 必须追踪每个 entry，成倍增加 scan 量
- `HashTrieMap.Load` 占 **5.97% flat / 10.56% cum**，是第二大热点

---

### 根因 3：IsVisible 每帧每单位重建 OwnerInfo

```go
// observer.go:85
func (os *Observer) IsVisible(mapUnit munit.IUnit) bool {
    relation := mapUnit.GetRelation(munit.NewOwnerInfo(cspb.TypePlayerOwner, os.ID, 0))
    // os.ID 固定不变，但每帧每个 entity 都重建并查 PlayerCache
```

调用链：`PackWildMapViewAck`(31.27% cum) → `GetVisibleCoverUnits`(17.20%) → `IsVisible` → `NewOwnerInfo` → `GetPlayerCache`

---

### 根因 4：PackWildMapViewAck 高频分配短命 map

每次调用分配 4-5 个 map/slice：
- `GetVisibleCoverUnits` 内：`units` + `filterUnit`
- `GetMarchingUnits` 内：`marchingUnits`
- `PackWildMapViewAck` 内：`noDelUnits`、`entities`

Cross server 在线玩家多，调用频率高，大量短命对象持续触发 GC，抬高 heap 水位。

---

### 根因 5：Observer.LastViewUnits 下线玩家未清理

```go
type Observer struct {
    LastViewUnits map[int64]munit.IUnit  // 视野内所有单位
    LogoutTime    int64                  // 下线时间
}
```

玩家下线后 Observer 保留（LogoutTime>0），`LastViewUnits` 持续持有大量 Unit 引用。Cross server 单位密集，每人视野数百条，多个下线玩家累积量不小。

---

### 根因 6：IsDead 无缓存每次遍历 map

```go
// battle/lineup.go:193
func (l *TroopData) IsDead() bool {
    return utility.SumMapValueByCond(l.GetSoldiersInfo(), ...) <= 0
    // 每次遍历 map[int32]*SoldierInfo，无缓存
}
```

在 `RangeBattleUnit` 循环中对每个战斗单位调用，共 **8.23s cum (11.54%)**。

---

## 优化建议

| 优先级 | 方案 |
|--------|------|
| P0 | Cross server 定期（如每小时）主动清理 `LastLoginTs` 超过若干小时的 PlayerCache |
| P1 | `Observer` 缓存 `selfOwnerInfo`，IsVisible 中直接复用，避免每帧 NewOwnerInfo + GetPlayerCache |
| P2 | 玩家 logout 时立即 `LastViewUnits = nil` |
| P3 | `GetVisibleCoverUnits` 中 sync.Pool 复用 map |
| P4 | `IsDead` 缓存总战力 |
| P5 | `PlayerCacheMgr` 从 sync.Map 改为 `map[int64]*PlayerCache` + RWMutex |
