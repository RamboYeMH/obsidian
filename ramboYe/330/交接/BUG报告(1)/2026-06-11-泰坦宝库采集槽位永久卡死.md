# BUG：泰坦宝库采集槽位永久卡死

## 现象

玩家反馈泰坦宝库"只能进两个队，第三队进不了"，后端返回 `ErrCodeTitanTreasureHouseTroopNumLimit`。

**复现路径**：远征图（cross server）上，玩家在泰坦宝库采集时，部队实体因某种跨服异常离开地图，但采集状态未清理，导致玩家的 `gatheringNum` 永久卡在上限。

**典型日志**（cross1007 17:41:17）：
```
[WAR] titan_treasure_house/titan_mgr.go:87
playerId = 6422422 CheckPlayerCanGather diff = [7649932796986012219 ...],
gatheringNum = 3, DefendTroops = [...], GatheringTroops=[7649932796986012219 ...]

[WAR] internal/ctl_titan_treasure_house.go:651
can not gather player = 6422422
```

---

## 根因分析

### 数据链路

| 数据结构 | 存储方式 | 作用 |
|---------|---------|------|
| `district.DefendTroops` | 持久化（MongoDB） | 当前宝库的驻守部队列表 |
| `GatherCtx.Gatherers` | 持久化（MongoDB） | 每个部队的采集进度，含 `OwnerId` |
| `PlayerGatheringTroop` | 纯内存（`bson:"-"`） | 玩家当前正在采集的部队 map，服务器启动时重建 |

### 触发条件

1. 玩家部队（`troopId=7649932796986012219`）在远征图泰坦宝库采集中途，部队实体**未走泰坦宝库 exit 路径**就从地图消失（跨服下线/清理触发了 non-standard 路径）
2. `DefendTroops` 和 `GatherCtx.Gatherers` 中保留了该部队的条目（持久化残态）
3. `PlayerGatheringTroop` 中也残留了该条目（`gatheringNum=3`，达到 `TitanMineGatherLimit=3` 上限）

### 代码漏洞（两处）

**漏洞 1 — `gatherMaxPTroopHandle`**（`suhongfan` 2025-07-08）

每个 tick 的 `GatherSettle` 检测到该部队 `endTs` 已过，触发 gatherMax，调用：

```go
func (wmap *WMap) gatherMaxPTroopHandle(_ *mtitan_treasure_house.District, troopIds []int64) {
    for _, troopId := range troopIds {
        if pt, ok := wmap.GetPlayerTroopByID(troopId); ok {
            wmap.RecallTroop(pt)
        }
        // ← 无 else：找不到部队时 PlayerGatheringTroop 永远不清理
    }
}
```

由于部队实体已不存在，`GetPlayerTroopByID` 返回 false，整个清理路径被跳过，每 tick 重复触发警告但始终无效。

**漏洞 2 — `titanTreasureHouseExit0`**（初始框架 `yangyuan`，OwnerId 逻辑 `suhongfan` 2025-07-08）

```go
func (wmap *WMap) titanTreasureHouseExit0(ptid int64, unit munit.IUnit, now int64) titan_treasure_house.Res {
    brief := titan_treasure_house.Brief{TroopID: ptid, AID: tt.GetAreaID()}
    if pt, ok := wmap.GetPlayerTroopByID(ptid); ok {
        brief.OwnerId = pt.OwnerInfo().ID
    }
    // ← 找不到时 OwnerId=0，RemovePlayerGatheringTroop(0, troopId) 是 no-op
    res := wmap.TitanTroopExit(brief, now)
    ...
}
```

服务器启动时的 init fix（`fixTitanTresureHouse`）也走这条路径，同样不能清理 `PlayerGatheringTroop`。

## 修复方案

### 代码修复（已提交 `h5_new_tf_v1044_bug`）

**Fix 1**：`gatherMaxPTroopHandle` 补 else 分支

```go
func (wmap *WMap) gatherMaxPTroopHandle(d *mtitan_treasure_house.District, troopIds []int64) {
    for _, troopId := range troopIds {
        if pt, ok := wmap.GetPlayerTroopByID(troopId); ok {
            wmap.RecallTroop(pt)
            tlog.Infof("=========TitanTreasureHouse Player: %v GatherMax", pt.OwnerInfo().ID)
        } else {
            // 部队实体已不在地图，直接调用 exit 清理残态
            if tt, ok2 := wmap.GetTitanTreasureHouseByID(d.GetUID()); ok2 {
                wmap.titanTreasureHouseExit0(troopId, tt, util.NowTs())
                tlog.Warnf("gatherMaxPTroopHandle troop %v not found, force exit", troopId)
            }
        }
    }
}
```

**Fix 2**：`titanTreasureHouseExit0` 从 `GatherCtx` 补全 OwnerId

```go
if pt, ok := wmap.GetPlayerTroopByID(ptid); ok {
    brief.OwnerId = pt.OwnerInfo().ID
} else if d := wmap.GetTitanDistrict(tt.GetAreaID()); d != nil {
    if g := d.GetGatherCtx().Get(ptid); g != nil {
        brief.OwnerId = g.OwnerId  // ← 从持久化的 Gatherer 取 OwnerId
    }
}
```

### 线上临时修复（无需发版）

**重启 cross1007**：
- `afterLoad()` → `fixTitanTresureHouse()` 先清除 `DefendTroops` 中找不到实体的部队
- `ServerStarted` → `serverStartLoadTitanGatherPlayer()` 从干净的 `DefendTroops` 重建 `PlayerGatheringTroop`
- 重启后玩家 gatheringNum 恢复正常

**无效方案**：GM 命令 `refreshTitanTreasure` 只清 `DefendTroops`，不更新内存中的 `PlayerGatheringTroop`，无效。
