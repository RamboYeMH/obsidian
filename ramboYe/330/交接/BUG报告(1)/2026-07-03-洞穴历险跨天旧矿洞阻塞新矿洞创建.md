# 洞穴历险：跨天后旧矿洞 Exist 状态阻塞新矿洞创建

## 问题描述

玩家点击洞穴历险活动中新刷出的5星洞穴，没有任何反应，也不会在地图创建洞穴。

## 复现步骤

1. 12:00 后生成一个5星洞穴并创建到地图上（State=Exist）
2. 23:59:50 左右派遣1支部队进入5星洞穴探索
3. 跨过24点后，洞穴历险活动洞穴刷新，刷出一个新的5星洞穴
4. 点击新刷出的5星洞穴 → **点击没反应，也不会在地图创建**

## 测试环境

- 环境：local-dev
- 玩家 ID：26649

## 根因分析

### 核心代码问题

**跨天刷新跳过 Exist 矿洞：** `comp_player_prog.go:150-151`

```go
func (this *PlayerMineProgress) refreshAllMines(contentID int32) map[int32]int32 {
    for i, one := range this.Mines {
        if one.State != cspb.ActvLostMineExist {  // ← Exist 状态直接跳过
            mineID := this.randomOneMineID(refreshCfg)
            resetMine(one, mineID)
        }
    }
}
```

**创建请求拒绝所有 Exist：** `ctl.go:204-210`

```go
for _, one := range pg.Mines {
    if one.State == cspb.ActvLostMineExist {
        ack.Err = cspb.ErrCodeLostMineCanExistOnlyOne  // 只要有一个 Exist，全部阻止
        msg_cast.SendMsg(playerID, ack)
        return
    }
}
```

### 故障链路

```
23:59:50  部队进入5星洞穴探索 → 矿洞 State = Exist（wmap 上有实体）
    │
00:00:00  跨天 onPlayerInitCheckNextDay 触发
    │
    ├─ refresh() → refreshAllMines()
    │   ├─ 旧矿洞 State=Exist → 跳过，不重置
    │   └─ 其他槽位 State=None → 重新随机 CfgID（可能出5星）
    │
    └─ sendAllInfoNtf() 推送给客户端
        → 旧=Exist + 新=None(含5星)
    │
客户端显示新5星洞穴（None 状态，外观可点击）
    │
玩家点击新5星洞穴
    │
    └─ 客户端检测到已有 Exist 矿洞
       → 不发送 CreateReq（或服务端返回 ErrCodeLostMineCanExistOnlyOne，
         客户端无 UI 反馈）
       → "点击没反应"
    │
13:01:08  旧矿洞才被 wmap 定时器删除 → State=Crashed
          → 但为时已晚，玩家已无法操作长达 13 小时
```

## 设计约定备忘

- 矿洞数量固定 3 个（`MineLimit = 3`），策划明确不配表
- `refreshAllMines` **故意跳过 Exist 状态**：避免替换正在使用的矿洞 CfgID
- 5星洞穴特殊处理：仅触发联盟订阅通知（`TemplateId=2017`），其余由配置表驱动
- `onMainBeforeMerge` 只重置刷新次数，不刷新矿洞 CfgID
- `packProto` 有 Deadline 检查（`NowTs() > Deadline` → Crashed），但只在异步回调中执行
- `sendAllInfoNtf` 不做状态校正，直接发送当前状态

## 修复方向（待确认）

1. **跨天强制清理 Exist 矿洞** — `onPlayerInitCheckNextDay` 中先重置 Exist→None/Crashed，再 refreshAllMines。wmap 旧实体通过定时器自行清理
2. **跨天对 Exist 矿洞做 Deadline 检查** — Deadline 已过才重置，未到期的保留
3. **放开"只能存在一个"的限制** — 允许同时存在多个矿洞（改动大，需评估影响）

## 附带问题

- `ActvLostMineItemRefreshAck` 多次在 gate 层超时（req expired），服务端已处理并发送 ACK，但 gate 找不到对应请求。可能是异步处理链路耗时过长或 gate 超时时间偏短
