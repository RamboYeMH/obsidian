IsExpInToEndStage() 只按时间戳判断"是否在远征战斗期"，不看 Match / Phase 状态字段。GM 把 StartTs 拨回历史日期后，5 个服的三个玩法被静默锁死约 35 天。

1结论摘要

一句话版本，赶时间只看这一节。

根因：IsExpInToEndStage()（game/play/internal/ctl_battlefield.go:2225）判断"当前是否处于远征进驻→结算阶段"时，只用 basic.StartTs 加配置阶段时长做纯算术，完全不读 basic.Match 和 basic.Phase。

2026-08-28 11:41 GM 执行 battlefield reset 2026-07-26 154 把 StartTs 拨回 7/26，随后 setmatchflag 0 / setphase 8 关闭远征。IsExpeditionOpen() 因此正确地变为 false（玩家进不去远征地图），但 IsExpInToEndStage() 按 7/26 推算出的时间窗 [07-30 00:00, 09-03 00:00] 恰好覆盖"今天"，于是恒为 true。

两个恒真条件相撞 → IsExpInToEndStage() && !p.InExpedition() 永远成立 → 玩法被永久拦截，玩家无任何操作可以绕过。

4根因分析

三层：状态字段被绕过 → 时间窗计算 → 两个恒真条件相撞。

4.1 IsExpInToEndStage() 是纯时间判断

// game/play/internal/ctl_battlefield.go:2225
// 远征阶段是否为 >=3 && <= 7        ← 注释说的是"阶段"，实现却是"时间"
func (play *Play) IsExpInToEndStage() bool {
    base := play.GetExpeditionBasic()
    if base == nil { /* ... */ return false }
    startTime, _ := play.GetPhaseStartTime(cspb.BFPBattleIn)   // 阶段 2 的起点
    _, endTime  := play.GetPhaseStartTime(cspb.BFPBattleEnd)   // 阶段 7 的终点
    nowTime := util.NowTs()
    return startTime <= nowTime && nowTime <= endTime        // 只有区间比较
}

GetPhaseStartTime()（game/play/internal/battlefield/mgr.go:303）同样是纯算术，输入只有两样：basic.StartTs 与剧本配置的阶段时长数组，不读 Phase，不读 Match：

phaseCfg := playbookCfg.ExpeditionStageTimes   // playbook=0 或配置缺失时回落 D2Const
startTime := base.GetStartTs()
endTime   := base.GetStartTs()
for index, durTime := range phaseCfg {
    if int(phase) >= index {
        dur := int64(durTime) * util.SecMs
        endTime += dur
        startTime = endTime - dur
    }
}

同文件里的对照组：IsExpeditionOpen() → BattlefieldMgr.IsOpen()（mgr.go:502）老老实实检查 StartTs>0 + Match + Phase 区间；IsExpeditionFiery() 也看 Match + Phase。10 个"远征是否进行中"的判断里，只有 IsExpInToEndStage() 走时间——它是这套判断族里唯一的异类。

误锁窗口 = 2026-07-30 00:00 ~ 2026-09-03 00:00，共 35 天，"今天"（08-28）落在正中间。

GM 用 2026-07-26 的本意是"退回上一次远征"，但一个远征周期按配置长达 39 天，退回 39 天以内的任何日期，都会让窗口重新覆盖当前时刻。要让窗口真正落在过去，reset 日期必须早于 今天 − 39 天（即早于 07-20）。这个陷阱对 GM 是完全不可见的。

4.3 两个条件同时恒真

// game/play/internal/ctl_bone.go:90
if play.IsExpInToEndStage() && !p.InExpedition() {
    ack.ErrCode = cspb.ErrCodeBoneNotInExp   // 25419 → "请到远征地图开启埋骨之地"

  • 条件一恒真：StartTs=07-26 使时间窗覆盖今天。
  • 条件二恒真：Match=false + marchinfo.mapinfo=null，远征副本根本不存在，玩家 MapType 永远是 0，进不去也就永远 !InExpedition()。

两者相乘 = 死锁。玩家做任何操作都无法自救，客服也无法指导。

4.4 同源隐患：battlefieldMatchFail()

本次事故的触发路径是 GM 命令，但代码里还埋着一条会自动触发同样问题的路径：

6改动方案

主方案一处改动覆盖全部 10 个调用点，不需要洗数据、不需要停服。

6.1 主方案：给 IsExpInToEndStage() 加状态闸门

文件 game/play/internal/ctl_battlefield.go:2225：

// 远征是否处于「进驻 → 结算」阶段（BFPBattleIn ~ BFPBattleEnd）
func (play *Play) IsExpInToEndStage() bool {
    base := play.GetExpeditionBasic()
    if base == nil {
-       tlog.Infof("IsExpDevilTime base is nil")
+       tlog.Infof("IsExpInToEndStage base is nil")
        return false
    }
+
+   // StartTs 可能被 GM reset 或 battlefieldMatchFail 回滚成历史日期，
+   // 此时纯时间判断会误判为"远征进行中"，必须先用状态字段闸门。
+   if !base.GetMatch() {
+       return false
+   }
+   if phase := base.GetPhase(); phase < cspb.BFPBattleIn || phase > cspb.BFPBattleEnd {

7.3 风险与遗留

  • 阶段字段与时间轴的短暂不同步：阶段推进由定时器驱动，理论上存在"时间已过点、Phase 字段尚未更新"的秒级窗口。此时新逻辑返回 false 而旧逻辑返回 true。影响仅限边界数秒内的玩法判定，且新行为更贴近真实状态，判定为可接受。
  • 脏数据服：若线上存在 Match=true 但 Phase 长期未推进的服，修复后这些服的远征限制会提前解除。上线前应抽查一批服的 battlefield.basic 确认不存在此类数据。
  • 未覆盖：本方案不解决"远征匹配出 CampMap 却 MapInfo=nil"这个上游问题（08-26 起连续三次匹配都是 nil），那是远征副本创建链路的独立故障，需另立单跟进。
  • GM 命令易用性：battlefield reset <日期> 的日期语义（必须早于今天减一个完整远征周期）对使用者不可见，建议在命令内加校验或提示，否则同类误操作还会发生。

7.4 验证方式

  1. 本地/测试服构造 Match=false, Phase=8, StartTs=今天−30天 的数据，确认 IsExpInToEndStage() 返回 false，埋骨可正常建造。
  2. 构造远征正常进行中的数据（Match=true, Phase=4），确认拦截逻辑仍生效、玩家必须在远征地图才能开。
  3. 上线后观察 src_location: internal/ctl_bone.go:92 与 [AltarRebellion] step=daily_schedule_skipped 两条日志归零。
  4. 核对 645 服次日 UnionAltarNextDay 是否正常创建定时器。

8经验教训

  • 同一个语义不要有两套实现。"远征是否进行中"在代码里存在 IsExpeditionOpen()（看状态）和 IsExpInToEndStage()（看时间）两套答案，甚至同一个文件 ctl_bone.go 里两个函数各用一套。平时等价，异常时分叉——而异常正是最需要判断正确的时候。
  • 派生值不能当事实源。StartTs 是可被 GM、可被回滚逻辑改写的字段，由它推算出的"当前阶段"不能反过来当作状态判断依据。状态字段（Match/Phase）才是事实源。
  • 注释与实现不一致会误导排查。IsExpInToEndStage() 的注释写着"远征阶段是否为 >=3 && <=7"，读注释的人会以为它检查了 Phase 字段，实际一行都没读。
  • 拦截类日志要打上判断依据。只打 playerId 的日志，只能证明"有人被拦了"，证明不了"为什么被拦"。把参与判断的字段一起打出来，排查成本从翻 mongo 降到看一行日志。
  • 静默跳过比报错更危险。埋骨/魔物至少有报错码能被玩家反馈上来；圣坛叛乱只是当天不生成定时器，没有任何人会发现——直到有人问"为什么这个月没叛乱"。
