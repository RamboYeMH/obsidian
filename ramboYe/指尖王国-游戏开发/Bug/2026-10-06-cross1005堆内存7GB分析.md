# cross1005 堆内存 7GB 分析

相关：[[2026-10-02-cross1005阵营3出生区被小号占满]]、[[战斗流程]]、[[行军流程]]

## 结论

- `cross1005_heap_20261006_221051.prof` 的 **inuse 是 7.32GB**。同一天 19:09 到 22:10 共 7 份 profile，一直在 6.7~7.9GB 之间，**这 3 小时内没有持续上涨**。这是常驻量，不是短时间的泄漏。
- 内存主要跟着**地图上存活的玩家部队（PlayerTroop）数量**涨。采样估算存活的 PlayerTroop 约 **15~17 万个**（19:09 是 16.2 万，20:40 是 14.8 万，22:10 是 17.3 万）。每支部队连同它挂着的消息数据、战斗上下文，大约要占 **30KB**。
- 占用最多的一块是 **natsrpc 用 jsoniter 解码出来、之后一直被部队引用的行军消息**，约 2.0~2.4GB。其中光 map 的桶就有 1.55GB：存活 map 约 180 万个、桶对象约 370 万个。

## 内存分布（inuse_space，总量 7.32GB）

| 归属 | 大小 | 说明 |
|---|---|---|
| natsrpc `handleReq` → `jsoniter.Unmarshal` | **2.03GB**（整个 natsrpc goroutine 2.41GB） | 行军消息解码出来的对象被部队直接引用，GC 回收不了 |
| 战斗 `WMap.fieldBattle` | **1.43GB** | `settleRound` 0.84GB，`RoundStart` 0.54GB |
| 行军建部队 `OnPlayToMapMarchSuccess` → `NewPlayerTroop` | 0.74GB | `InitBattle` 0.49GB（BatCtx、TroopData） |
| 启动和配置（`main.Start`） | 0.63GB | gdconf、nav mesh（0.18GB）、i18n 等 |
| DB worker bson 加载 | 0.57GB | 启动时从 Mongo 加载的地图单位 |
| 定时器回调 | 0.47GB | |
| 视野 ObView / Grid 等 | 约 0.3GB | `addObserver`、`AddMarchingUnit`、`Grid.addEntity` |

### 1. natsrpc 解码出来的对象（约 2GB，最大头）

入口在 `natsrpc/internal/handler.go:50`：

```go
msg0 := reflect.New(tp.Elem()).Interface()
jsoniter.Unmarshal(req.Data, msg0)
```

按解码栈的结构把大头对应到了 `iproto.PlayToMapMarchSuccess`（`game/iproto/p2m.go:525`）上：

| 解码路径（jsoniter 栈结构） | inuse | 对应字段 |
|---|---|---|
| struct → *struct → *struct → map（placeholder） | **921MB** | `OriginReq.ExtraInfo`（`*gdconf.TroopExtraInfo`）里面的 `SameCampActvPty map[int32]float64` 和 `SoldiersLevel map[int32]int32` |
| struct → *struct → []*struct → map | **436MB** | `OriginReq.Heroes[].Props map[int32]float64`（英雄全量属性） |
| struct → *struct → map | 114MB | `OriginReq.Soldiers`、`SoldiersInfo`、`ExtraSkillCfgList` |

> 说明：jsoniter 给同一个顶层类型生成解码器时，同一种类型第二次出现就会用 `placeholderDecoder`。`map[int32]float64` 第一次出现是在 `Heroes[].Props`，`map[int32]int32` 第一次出现是在 `Soldiers`，所以 `ExtraInfo` 下面的这两个 map 都会走 placeholder。这一项只是按栈结构推断出来的，profile 里没有类型名。

这些对象一直不释放的原因：`WMap.OnPlayToMapMarchSuccess`（`game/wmap/internal/ctl_lineup.go:844`）把 `reginReq.GetExtraInfo()`、`Heroes`、`ExtraSkillCfgList` **直接按指针**传给 `NewPlayerTroop` → `battle.NewBattleBehavior`（`game/wmap/internal/mmap/melem/mtroop/player_troop.go:93`），没有做精简或复制。所以部队活多久，整个解码出来的消息就被留多久。

每个 map 都很大，原因如下：
- `TroopHero.Props` 来自 `HeroMgr.GetProps` → `computePropsContainer`（`game/play/internal/mplayer/mhero/mgr.go:489`），是英雄**所有来源的全量属性**，不只是战斗要用的那些。
- `SameCampActvPty` 由 `calD2HeroMarchCampsCfg`（`game/play/internal/ctl_lineup.go:3866`）累加：阵营羁绊、战魂刻印 `PourLineupBuffs`、巨龙战甲、Lineup 作用域的 buff、皮肤、宠物装备都往里加，属性条目很多。

### 2. 战斗上下文（1.43GB）

- `battle.getDetailByTroopID`（`game/wmap/internal/battle/battlectx.go:618`）：**394MB，约 258 万个 `BMLPageDetail`**。这是每个敌方部队一份的战报分页数据，`pageInfoEnd` 每回合会把它 `AddRoundInfo` 追加进 `TroopData.RoundInfo`（`game/wmap/internal/battle/lineup.go:107`）。
- `battle.newBatCtx`（`battlectx.go:289`）：331MB，其中 BatCtx 结构体本身 273MB。
- `TroopExtraInfo.DeepCopyInto` 150MB、`TroopData.DeepCopyInto` 260MB：这些是存盘或快照时复制出来的。

⚠️ 可能会一直涨的点：`TroopData.ClearRoundInfo`（`game/wmap/internal/battle/lineup.go:112`）**只要有任意一个敌方部队还没有 UseRecord（还没出战报邮件）就直接 return**，整个 `RoundInfo` 都不清。`RecordBattlestatusReport` 对野怪战斗不做记录。对于存活时间很长、要和很多部队打的单位（驻防部队、城防），要是某个对手一直没出邮件，就会一直攒着 `[]*BMLPageDetail`。

### 3. 内存分配频率（alloc_space，次要问题）

natsrpc 解码这一块累计分配了 **670GB**：`Iterator.ReadString` 334GB，`base64.DecodeString` 242GB。说明有某条 nats JSON 消息带了很大的 `[]byte` 或字符串字段（JSON 里的 `[]byte` 会被编成 base64），而且发得很频繁。它不影响常驻内存，但 GC 压力很大。

## 待确认 / 建议

1. **先确认部队数量对不对得上（最关键）**：用 GM 或日志统计 cross1005 的 `UnitMgr` 里实际有多少个 `MapUnitPlayerTroop`。
   - 如果真的有 15 万以上：说明内存就是被规模撑起来的。远征 4 个阵营，每个阵营 12 个服；另外还有 [[2026-10-02-cross1005阵营3出生区被小号占满]] 里那几百个挂机小号，它们的驻防部队一直留在图上。
   - 如果明显少于这个数：说明有**已经移出地图、但还被别处引用的部队**（可以重点查 ObView 观察者、timer、集结列表、BatCtx 互相引用）。这种情况算泄漏。
2. **精简跨服行军消息**：`TroopHero.Props` 只传战斗用得到的属性 ID，或者到了 wmap 这边改成紧凑的 slice 或数组再存。`SameCampActvPty` 也一样处理。现在一支部队光这几个 map 就要 10KB 以上。
3. **不要直接持有解码出来的整条消息**：在 `createMarchUnitNew` 里只取需要的字段，让 `PlayToMapMarchSuccess`/`OriginReq` 的其余部分能被 GC 回收。
4. **`ClearRoundInfo` 的提前 return**：改成只删除已经有 UseRecord 的条目（跟 `CheckRoundInfoUseRecord` 一样的逻辑），或者给 `RoundInfo` 加上限、过期时间。
5. 查一下是哪条 nats 消息带了大的 base64 字段，用 `go tool pprof -sample_index=alloc_space -peek 'base64.*DecodeString'` 配合 RPC 名的日志来定位。
