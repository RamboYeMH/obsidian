# H5-5400 唯一ID生成器 counter 位溢出导致 ID 重复

> **一句话总结**：把多个字段按位拼成一个 int64 时，**每段的宽度只是约定，代码没有截断保证**。其中一段的值涨过了自己的位数，就会伸进隔壁那段，用 `|` 合并时信息被吞掉，导致 ID 重复。
> 这是"**位宽上限 / 位域溢出**"类问题的典型案例。

## 现象

- Jira：H5-5400【指尖王国V1032】生成唯一id代码没有重置功能（报告人 yuejian，P1）
- 期望：唯一 ID 不重复
- 实际：ID 重复，导致邮件内容显示错误、活动数据错误等
- 样例 ID：`7580767601362333620`

## 代码位置

ID 生成器在 tse 库：`../tse/core/util/idgen/idgen.go`（gs 的 go.mod 用 `replace git.tap4fun.com/fw/tse => ../tse`，vendor 里有副本）

```go
// idgen.go:33
var idCounter = int64(0)

// idgen.go:39
func Init(sid int32) {
	serverID = int64(sid)
}

// idgen.go:44
func NewID() int64 {
	counter := atomic.AddInt64(&idCounter, 1)          // 全局累加，从不截断、从不重置
	now := timeutil.ToUTC(time.Now()).Unix()
	return (now << 32) | (serverID << 18) | counter
}
```

- 每个进程启动时调 `idgen.Init(conf.ServerID)`，如 `game/main.go:85`，global / cross / rank / actv / jabber / webserver / door / pay 也一样
- gs 里共有 424 处调用 `idgen.NewID()`（wmap / play / actv / cactv / mail 等）

## 一、ID 是怎么拼出来的

### 64 位布局

```
 63                      32 31            18 17               0
| ------ 时间戳 32位 ------ | serverID 14位 | --- 计数 18位 --- |
```

| 段 | 起始位 | 宽度 | 宽度怎么来的 |
|---|---|---|---|
| 时间戳 now | 32 | 32 | 64 − 32 |
| serverID | 18 | 14 | 32 − 18 |
| counter | 0 | 18 | 18 − 0 |

> ⚠️ 代码里**只写了每段的起始位**（`<< 32`、`<< 18`），**宽度是靠相邻两段的起点相减推出来的隐含约定**，没有任何截断去保证它。这是问题的根源。

### 三个位运算符

**1. `<<` 左移**：`x << N` = 末尾补 N 个 0 = 每一位往左挪 N 位 = `x × 2^N`

```
5      = 101
5 << 3 = 101000 = 40
```

- N 表示"**从第 N 位开始放**"，也就是右边给别人留了 N 位，**不是"取 N 位"**
- int64 只有 64 格，右边补 N 个 0，左边最高 N 位会被挤掉丢弃

**2. `|` 按位或**：同一位上只要有一个是 1，结果就是 1

```
12 = 1100
 3 = 0011
---------- |
     1111 = 15
```

- 各段互不重叠时，`|` 等于把各段拼起来（效果和 `+` 一样）
- 两段**在同一位上都是 1** 时，`1 | 1 = 1`，两个 1 合成一个，**信息丢失**

**3. `&` 按位与 + 掩码**：两个都是 1 才是 1。和"低 N 位全是 1"的掩码做 `&`，就只保留低 N 位

```
0x3FFFF = 3    F    F    F    F
        = 11 1111 1111 1111 1111   ← 18 个 1 = 262143 = 2^18 − 1 = (1<<18) - 1
```

### 用样例 ID 走一遍

`7580767601362333620` 拆开：now = 1765035000（2025-12-06 15:30:00 UTC），serverID 段 = 255，counter 段 = 126900

```
now<<32  = 0110100100110100010010111111100000000000000000000000000000000000
sid<<18  = 0000000000000000000000000000000000000011111111000000000000000000
counter  = 0000000000000000000000000000000000000000000000011110111110110100
------------------------------------------------------------------------- |
结果     = 0110100100110100010010111111100000000011111111011110111110110100
```

反解：时间戳 = `id >> 32`；serverID = `(id >> 18) & 0x3FFF`；counter = `id & 0x3FFFF`

> 注意：变量**类型**是 int64，有 64 格，但**值**很小时高位全是 0，左移时被挤掉的也是 0，不影响结果。出问题的是值大到高位不再是 0 的情况。
> 计算机里整数本来就是二进制存的，位运算直接作用在这 64 个 0/1 上，不存在"转二进制"这一步。

## 二、根因：counter 涨过 18 位，伸进 serverID 区

`counter` 从进程启动起**累计**自增，从不截断。进程累计生成 262144（2^18）个 ID 后，它就变成 19 位、20 位……多出来的高位落进 serverID 区，再被 `|` 吞掉。

| 进程启动后累计生成的 ID 数 | counter 位数 | 后果 |
|---|---|---|
| < 262,144 | ≤ 18 | 正常 |
| 262,144 ~ 524,287 | 19 | 盖到 serverID 最低位 |
| 52 万 ~ 104 万 | 20 | 盖到 serverID 低 2 位 |
| > 42 亿（2^32） | > 32 | 连时间戳段都被污染 |

### 撞 ID 的例子

两台服都按正常速度生成 ID，每秒只有几个：

```
服 A：serverID = 4 (100)，跑了几天，counter = 262147 = 1 000000000000000011
服 B：serverID = 5 (101)，刚重启，  counter = 3      =   000000000000000011

服 A：  100 000000000000000000
      |   1 000000000000000011     ← counter 第 19 位伸进 sid 区
      = 101 000000000000000011     ← sid 段被或成 5

服 B：  101 000000000000000011

同一秒内 → 两个 ID 完全相同
```

关键点：
- 现在的问题跟**每秒生成多少无关**，**只要进程跑得够久**（累计超过 26 万个）就会触发
- 撞的主要是**不同服之间**：serverID 被污染后，A 服的 ID 看起来像是 B 服生成的
- 被污染后，只看 ID 本身**无法分辨**真实的 serverID 和 counter。样例里 serverID 段 = 255，可能真是 255 号服，也可能是更小的号被或成了 255

源码注释写着"支持每秒生成 2^18 个 ID"，描述的是**设计意图**，代码没有实现它。

### 十进制类比

```
服务器号 07 × 10^3 = 07000
序号 12345        = 12345   ← 超过 3 位
相加              = 19345   ← 服务器号被污染成 19
```

## 三、修复方案

### 最小改法：counter 截到 18 位

```go
counter := atomic.AddInt64(&idCounter, 1) & 0x3FFFF
```

- counter 永远只有 18 位，碰不到 serverID，**跨服重复彻底消除**
- 不用加锁，改一行
- 新 ID 的时间戳都是新的秒数，不会和库里已有的旧 ID 冲突

### 截断后的回绕

```
  111111111111111111      (262143)
+                  1
= 1000000000000000000     (262144)
& 0111111111111111111     (0x3FFFF)
= 0                       ← 回到 0
```

counter 循环：0 → 262143 → 0 → …（`idCounter` 变量本身还是一直涨，只是放进 ID 的部分被截断）

**回绕会不会重复？** 看上一次用同一个计数值是不是也在同一秒：
- 两个相同计数值之间隔了 262144 次生成。这 26 万次跨了秒，时间戳就不同，**不重复**
- 只有**单进程一秒内生成超过 262144 个**，才会重复。实际业务远达不到
- 单里提的"每秒重置"方案也是同样的上限，和截断等价

### 现在 vs 修复后

| | 现在 | 加 `& 0x3FFFF` 后 |
|---|---|---|
| counter 超 18 位 | 累计 26 万后必然发生 | 不会，回绕到 0 |
| 何时重复 | 进程跑久了，跨服之间撞 | 单进程一秒超过 26 万个 |
| 实际风险 | 高 | 可忽略 |

### 更清晰的写法（推荐）

把宽度显式写出来，每段都截一下：

```go
const (
	counterBits  = 18
	serverIDBits = 14
)

func NewID() int64 {
	counter := atomic.AddInt64(&idCounter, 1) & (1<<counterBits - 1)
	sid := serverID & (1<<serverIDBits - 1)
	now := timeutil.ToUTC(time.Now()).Unix()
	return (now << (serverIDBits + counterBits)) | (sid << counterBits) | counter
}
```

### 彻底杜绝：snowflake 方式

记录上次生成的秒数，同一秒内计数用完一圈就等到下一秒再生成。理论上永不重复，代价是要加锁、代码更复杂。以目前的业务量没有必要。

### 发布注意

- 改的是 `../tse` 仓库 `final_h5` 分支，改完要同步 gs 的 vendor
- 所有用 idgen 的服（game / global / cross / rank / actv / jabber / webserver / door / pay）都要重新编译、发布
- tse 仓库所有分支都没修（`origin/dev_ice` 只是把 `<<18` 改成 `<<21`，counter 仍然不截断，不算修复）。评论里说的"做了，但是你们没更新"在 tse 仓库里找不到对应提交

## 四、同类上限：其他两段也有

| 段 | 代码限制 | 上限 | 越界后果 | 风险 |
|---|---|---|---|---|
| counter | 无 | 累计 262143 | 伸进 serverID 区 | **必然发生**（本 Bug） |
| serverID | 无 | **编号**值 ≤ 16383 | 伸进时间戳区 | 看配置，目前 door=2011、pay=2012，未超 |
| 时间戳 | 无 | 2^31 / 2^32 | 2038-01 ID 变负数；2106 年最高位被挤掉，开始重复 | 远期 |

- serverID 看的是**编号的数值**（配置的 ServerID），不是进程数量，也不是系统 PID。所有进程共用一个号段，必须 **< 16384 且互不相同**
- 截断管不到的情况：serverID 配重复、时钟回拨、同一秒内重启

## 五、经验总结（通用）

1. **位拼接的每一段都要显式截断**：`(x & mask) << shift`。只写 shift 不写 mask，等于把"值不会超宽"的假设交给运气
2. **累加型字段最危险**：配置值是固定的，越界在上线前就能发现；计数器会一直涨，**测试环境跑不出来，线上跑久了才炸**
3. **`|` 会静默吞掉信息**：段重叠时不报错、不 panic，只是悄悄产出错误的值。换成 `+` 也一样，进位照样把数据搞乱
4. **注释 ≠ 实现**：注释写"每秒 2^18 个"，代码并没有实现每秒语义
5. **常量命名代替魔法数**：`counterBits = 18` 比 `<< 18` 和 `0x3FFFF` 清楚得多，宽度和起点一眼可见
