服务端为什么没拦住

  1. door 收到推送后发 D2PGiftTimeLimitRecordNtf，game 端调用 TiggerGiftTimeLimit（game/play/internal/ctl_gitf_time_limit.go:106），用 cfg.BuyLimit 当 countMax。
  2. addGiftTimeLimitRecordByGm（game/play/internal/ctl_d2iap.go:2079）里的去重条件要求"未过期且类型不同"才跳过。运营推送的 LimitTimeTyp 都是 0，前后相等，所以条件永远不成立。
  3. 于是新推送直接覆盖 GiftTimeLimitRecords[giftId]，CurCount: 0 被重置，玩家又能买一次。
// 如果已经有记录了，并且没有过期 不在触发新的 if util.NowSecTs() < records.GetEnd() && records.LimitTimeTyp != giftLimitTimeTyp { return } ... shopRecord.GiftTimeLimitRecords[gift.Id] = &mplayer.GiftTimeLimit{ ..., CountMax: countMax, CurCount: 0, ... }

建议

  • 运营 / 推送平台（主因）确认这个礼包的推送策略，看是不是配了"买完再推"或者"没有限制地重复推"。推送日志里的 push_id 和 ops_request_id 都能对上。
  • 服务端保护（可选）同一个礼包还有未过期记录、并且已经买满时，忽略同类型的重复推送，或者不重置 CurCount。要不要这样改，需要先和策划、运营对一下当初的设计意图。
  • 历史今天之前 boughtCount 已经是 53，这个玩家之前也多次买过这个礼包，大概率是同样的原因。线上日志只保留约 20 天，更早的查不到。
