H5 战损礼包买完首个礼包后限时礼包入口消失：代码与配置核查报告

核查日期：2026-11-05 · H5 · 双端源码与最新配表只读核查（对标 K3 S156 限时礼包入口消失案）
基线：客户端 k3client d8a752ef117d（2026-10-28）· 服务器 gs 921c045b3403（2026-10-29）· 配表 配置表/TD(最新)/Gift.xlsx
源码层面存在同款缺陷影响程度待实测确认重登无法自救

H5 不仅原样存在 K3 报告定位的 3 处双端代码缺陷，而且因为 H5 在自动拍脸、支付回调与弹窗刷新上的 4 处差异，从源码推演玩家受影响程度可能比 K3 更重（尚未在测试服实测，见第六、七节）。

当玩家同时触发普通弹窗礼包（Type=19）与战损礼包（Type=39，2700001~2700004）或仅触发战损礼包时，买完第 1 个礼包后弹窗立即强关、主城左侧按钮当场消失；且 H5 战损礼包配为 DayTimes=1, CdTime=0，玩家连靠重新登录触发拍脸自救的途径也被彻底堵死。（A）

一、先回答：H5 有没有这个 Bug

问题点 1 · 同 K3
主城按钮漏判 Type=39
弹窗内 PopGiftMgr 认 Type=19/39，但主城按钮 HeroPopGiftMgr.CheckHasGift 只查 Type=19，没有 19 时入口直接隐藏。
问题点 2 · 含 H5 陷阱
买单档即强关整个弹窗
UIGiftWidget 买任意 1 个即调用 ClosePopup；且 H5 的 UIGiftPopup.OnOpenStart 空列表未调 Close()，直删会留空壳。
问题点 3/4 · H5 差异
已购状态不同步 + 拍脸死锁
服务端对 Type=39 只下发 bought 为购买前旧值的 isRecharge=false 推送，带正确次数的充值推送被拦截（不直接导致入口消失）；客户端 DayTimes=1 与 CheckPopGift 耦合封死重登拍脸。

结论：K3 案例中的每一条故障机制在 H5 均未修复，且 H5 修复时若照搬 K3 客户端改动而不补 UIGiftPopup.OnOpenStart 的 Close()，还会引入“买完最后一档残留空弹窗”的新 Bug。（A）

成因归属：“入口消失”的直接成因是问题点 1（主城按钮漏判 Type=39）与问题点 2（买单档强关弹窗）；问题点 3 影响的是战损礼包购买后的已购状态与支付回调，与入口显隐无直接因果，单列处理。（A）

四、原因与处理方案（客户端）：入口漏判与买单档强关

问题点 1：主城左侧按钮显隐与倒计时漏掉 PvpDeadGift（P0）

HeroPopGiftMgr.CheckHasGift()（HeroPopGiftMgr.cs:79）只查询 GameData.I.GiftData.GetPeriodGiftDats(GiftTypeEnum.PopGift)（Type=19），GetMinInvalidTime()（:48-66）也只遍历该列表。当弹窗内只剩 Type=39 战损礼包时，CheckHasGift() 返回 false，UIMain_SpecialActivityWidget.cs:419 立即隐藏主城入口。

修复方案：将 HeroPopGiftMgr.cs:79 改为 GameData.I.GiftData.GetPeriodGiftDats(GiftTypeEnum.PopGift, GiftTypeEnum.PvpDeadGift)（GetPeriodGiftDats 原生支持变长参数）。（A）

问题点 2：买单档即强关整窗 + H5 空列表未关窗陷阱（P1）

UIGiftWidget.OnBtnBuyClick（UIGiftWidget.cs:413）与 OnBuyItemFunc（:445）点击购买即调用 PopupManager.I.ClosePopup<UIGiftPopupPop>()。但注意 H5 差异：H5 收到 PaySuccess 后走 UIGiftPopup.RefreshShowUI -> OnOpenStart()（UIGiftPopup.cs:445-448），当 mDataList.Count == 0 时只 return 未调 Close()！

修复方案：① UIGiftWidget.cs 在多页签未买完时不调 ClosePopup；② 同步在 UIGiftPopup.cs:445 的 if (mDataList.Count == 0) 分支补上 Close();，防止买完最后一档残留空壳弹窗。（A）

五、原因与处理方案（服务端与拍脸）：推送拦截与重登死锁

问题点 3：服务端战损礼包购买后已购状态推送缺失，H5 客户端 LPay 回调断链（P1，非入口消失直接成因）

服务端 delGiftTimeLimitRecord（ctl_d2iap.go:2009-2024）在 RecordShopping 之前执行（战损礼包记录的 TargetId 由 AddPvpLoseRecord 以 idgen.NewID() 生成，必然 > 0），先对 record.CurCount++ 并发送 isRecharge=false 的 UpdateGiftNtf；由于 GetGiftBoughtCount 读取的是 RecordShopping 写入的购买记录，此时 bought 仍是购买前旧值（首购为 0）。随后 SendUpdateGiftNtf（:1087-1089）遇到 GiftTypeBattleLossGift(39) 直接 return。而在 H5 中，LPay.OnBuySuccessNtf（LPay.cs:904-907）判断 (bool)args[1] == false（即 isRecharge == false）时直接 return，导致购买战损礼包后客户端支付成功回调 _actionList 与历史购买次数累加失效，且客户端收不到任何一条已购次数正确的推送。

历史背景：该 return 由 7ff1cd1f5c（2024-01-30，攻击补偿）引入，当时函数只处理单个礼包，含义是“战损礼包不推送”，属有意设计；be891f480c（2024-08-24，优化礼包推送）改为批量推送时沿用了 return，才变成“整批丢弃”。整批丢弃只会发生在 GiftTrigger（ctl_d2iap.go:890）与多选一分支，且前提是 39 号礼包混入其列表；战损礼包走 PVP 积分触发路径，正常不会混入，因此“同批新礼包被吞”属理论风险而非已发生问题。（A）

修复方案：① SendUpdateGiftNtf 中的 return 改为 continue，消除整批丢弃风险；② 将 delGiftTimeLimitRecord 的推送移到 RecordShopping 之后（或推送时 bought 补 +1），保证已购次数正确；③ 是否对战损礼包恢复发送 isRecharge=true 推送，需先与客户端确认当初跳过的原因及 LPay 实际依赖的消息后再定，避免重复弹窗等副作用。（B）

问题点 4：H5 特有的 3 重自动拍脸死锁（P1）

  • 限制一（配表与去重）：15001~15004 配了 DayTimes=1, CdTime=0, TabOrder=2（AutoOpenMgr.cs:581-608），非登录切回主城因 CoolDownTime==0 永不弹出，登录时同属 TabOrder=2 只弹 1 个且弹完 1 次即耗尽当日额度。
  • 限制二（错误耦合普通礼包）：AutoOpenMgr.PopGiftCheck（AutoOpenMgr.cs:938-943）拼接了 && PopGiftMgr.I.CheckPopGift(true)，后者校验的是 GiftTypeEnum.Common(1) 普通周/月常驻礼包（PopGiftMgr.cs:465-496），普通礼包售罄即连坐封死 Tab=1 自动拍脸。
  • 限制三（今日不再弹出）：勾选 UIDailyMuteToggle（UIGiftPopup.cs:281-284）会将整个 PopGiftTypeEnum_1 当日静默。

修复方案：移除 AutoOpenMgr.PopGiftCheck 中对 CheckPopGift(true) 的错误耦合，并由策划评估将 15001~15004 的 DayTimes / CdTime 调整为允许冷却后重弹。（A）

六、如何复现与回归验收

  1. 复现路径：测试服账号同时触发 1 个 Type=19 弹窗礼包（如 4000021）与任意档位 Type=39 战损礼包（如大地图 PVP 死兵满 10 万触发 2700001）；打开主城左侧限时礼包弹窗，购买第 1 个页签（4000021），观察到弹窗立即关闭、主城左侧限时礼包按钮消失、重登也不再弹出剩余战损礼包。
  2. 主城入口与倒计时回归：修复后，当账号仅有未购买的 2700001~2700004（无 Type=19 礼包）时，主城左侧 HeroGift 按钮正常显示，倒计时与最快过期的战损礼包一致。
  3. 多页签连续购买与末档关窗回归：弹窗含多个页签时，买完第 1 个页签后弹窗保持打开并自动刷新切换到剩余未买页签；买完最后 1 个页签后弹窗自动关闭，不留空壳界面。
  4. 战损礼包支付回调回归：直接购买 2700001~2700004，验证服务端下发的 UpdateGiftNtf 中 bought 为购买后的正确次数（如与客户端确认需要，再验证 isRecharge=true 推送），客户端 LPay.OnBuySuccessNtf 正常触发发奖弹窗与历史次数累加。

以上复现与回归项基于源码确定性推演，待研发合入补丁后在测试服实机执行。（D）
