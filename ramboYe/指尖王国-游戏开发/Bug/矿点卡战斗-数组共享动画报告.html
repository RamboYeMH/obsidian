从一块共享数组说起

① 共享的是数组，不是长度

把数组想成一排柜子，把切片想成一张登记卡。卡上写着“从哪个柜子开始、当前使用几个、最多可用几个”。复制登记卡不会复制柜子。

切片头                 底层数组                         战斗对象
WhoAttack ───┐         ┌────────┬────────┬────────┐
             ├────────→│ A 指针 │ B 指针 │ C 指针 │
EndAttackInfo┘         └───┬────┴───┬────┴───┬────┘
                          ↓        ↓        ↓
                         A对象    B对象    C对象

两张登记卡各自独立

len 是当前有效元素个数；cap 是从起点可使用的容量。改变 WhoAttack.len，不会改变另一张卡的长度。

数组格子共同使用

同一格被改写，两张卡都能看到。格子里存的是 *BatCtx 指针；复制指针不会创建一支新部队。

共享发生在这里

// BatCtx.GiveupTarget · battle/battlectx.go
curTarget.SetEndAttackInfo(curTarget.GetWhoAttack());
curTarget.otherGiveupTarget(t);

// 生成的 setter · battle/accessor_BatCtx.go
func (p *BatCtx) SetEndAttackInfo(value []*BatCtx) {
    p.EndAttackInfo = value // 只复制切片头，没有复制数组
}

当追击者 X 放弃玩家队伍 D 时，curTarget 就是 D。上面相当于 D.EndAttackInfo = D.WhoAttack。

末两步聚焦 WhoAttack 的删除效果，省略各次死亡附带的临时收尾名单生成与清空，不把该表当作全部函数调用的逐指令快照。
三个容易混淆的细节
  1. X 去哪里了？删除后 len=0，追加 A 从下标0写入，直接覆盖 X 的指针。append 不会检查那一格有没有旧值。
  2. 为什么删除 A 变成 [B,C,C]？原地删除是把 B/C 复制到前两格，最后一个旧 C 没擦掉。新 WhoAttack 长度只有2，第三格不属于它的有效内容。
  3. 为何 append 不保护另一张名单？它只知道接收切片自己的 len/cap，不知道其他切片是否也使用这些格子。EndAttackInfo.len=1，就写下标1。


② 为什么 EndAttackInfo 没清理
先区分：被别人攻击，不等于自己有攻击目标
攻击方设置目标时，就会把自己加入 D.WhoAttack。随后才调用 JoinBattlePassive，尝试让 D 反击。但这个函数可以提前返回。
// JoinBattlePassive · ctl_battle.go（关键片段）
march, exist := beAtk.GetMarch()
if !cspb.IsMapUnitNpcTroop(beAtk) && exist &&
    march.GetAction() != cspb.MarchActStubAct {
    return false // 赴矿行军的个人队伍在这里返回
}
// 只有通过判断，才设置防守方的攻击目标
battle.SetBattleCurTarget(beAtk, atk)
X.CurTarget = D    // X 正在追击 D
D.WhoAttack = [X]  // D 知道有人攻击自己
D.CurTarget = nil  // D 继续行军，没有设置反击目标
到矿后行军结束，这个行军条件不再拦截。所以“赴矿追击”与“矿点围攻”可以表现不同。
留下引用后，个人部队在这个分支直接返回
// WMap.giveUpTarget · ctl_battle.go（省略日志与注释）
ownerBatCtx.GiveupTarget() // 已经设置 D.EndAttackInfo
// ……
if targetCtx.GetCurTarget() == nil {
    if targetBatUnit, ok := melem.UnitToIBattleUnit(target); ok {
        wmap.settleBattle(targetBatUnit, owner)
        if _, isRt := melem.UnitToRallyTroop(target); isRt &&
            !targetBatUnit.BatCtx().InBattle() {
            wmap.battleEnd(targetBatUnit)
        }
        return true
    }
}
D 没主目标 → 进入分支；D 是个人编队 → isRt=false；跳过 battleEnd(D) → 直接 return。
settleBattle 的交战结算不等价于整套部队收尾。这条路径没有清掉 D.EndAttackInfo。
实际清理在哪里
// DelUnionAttackInfo · ctl_union.go（个人部队分支片段）
if pt.CityID == 0 {
    return
}
// ……
ptBatCtx := pt.BattleBehavior.BatCtx()
atkIds = ptBatCtx.GetAttackTroopIds()
ptBatCtx.SetEndAttackInfo(nil)
相关收尾链是 battleEnd → pTroopBattleEndAlive → 对应分支调用 DelUnionAttackInfo。前面的提前返回漏掉这次清理。清理函数自身也有条件，不能说每次 battleEnd 都必然清空名单。
最后一个追击者退出后，D 的 WhoAttack 已空、CurTarget 为空，InBattle 返回 false；普通非战斗 tick 不会自动补做这份名单的清理，因此旧引用有机会留到后续交战。


③ 为什么死亡攻击者会残留
顺序决定结果：先删除，再被写回
// WMap.battleTroopDead · ctl_battle.go（关键片段）
unitCtx := unit.BatCtx()       // unitCtx = 死亡的 A
exitTroops := unitCtx.TroopDead() // 通知 D.otherDead(A)，先删掉 A
// ……
for _, id := range exitTroops {
    // ……查找对应地图部队……
    atackCtx := atkBatUnit.BatCtx() // 处理到 D 时，atackCtx = D
    atackCtx.EndAttackInfo = append(atackCtx.EndAttackInfo, unitCtx)
    wmap.battleEnd(atkBatUnit)
}
A 正在攻击 D 时，TroopDead 会把自己的目标 D 纳入返回名单。不能因为变量叫 atk，就认为这个循环不会处理 D。
正确删除 A 后： WhoAttack = [B,C]
收尾 append A： WhoAttack = [B,A]  ← C 被覆盖
B 后来死亡：    WhoAttack = [A]
C 后来死亡：    名单里已没有 C，无法删除
A 已死过：      正常死亡清理不会自动再执行一次
清掉 EndAttackInfo 也无法撤销覆盖
EndAttackInfo = nil 只是扔掉一张登记卡。数组第二格已经被写成 A，WhoAttack 仍拿着这份错误数据。
地图实体删除，不会自动清理所有引用
其他名单仍可持有 A 的 BatCtx 指针。Go GC 不负责修复业务关系，也不会自动从 D.WhoAttack 删除 A。这是业务失效引用，不是内存悬空指针。
由残留关系演变为卡战斗和采集异常
WhoAttack=[A] 且 StartBattleTime>0
                 ↓
InBattle() 仍为 true，但主目标为空
                 ↓
battlePrepare：找不到目标0 → giveUpTarget → battleEnd

                         TroopResetGatherCtx

战斗状态判断又排在采集、行军状态之后，客户端持续显示「战斗中」。重登只重新获取服务器状态；本案回城销毁 D 的地图实体后恢复。
这是定时器反复执行异常收尾，不是阻塞事件循环的紧循环。本次线上采样间隔约1.1秒。“残留”指正常事件无法自然清掉，仍可能被显式修复或实体销毁打断。


触发边界：共享数组，不代表每次都出错
对于本例两个切片起点相同的情况，令 e=len(EndAttackInfo)、w=len(WhoAttack)，其中 w 是死亡删除后的长度。
覆盖有效元素需要同时满足：仍共享数组；e < cap(EndAttackInfo)，追加不扩容；e < w，写入点落在受击名单有效范围内。
后续只有一支敌军 C
C 死亡后 WhoAttack.len=0。即使收尾名单追加写了下标1，也不会把 WhoAttack 的长度变回非零。因此不会形成这里讲的死亡对象回写残留。
后续三支敌军 A/B/C
A 死亡后 WhoAttack.len=2，旧 EndAttackInfo.len=1；追加写下标1，恰好覆盖有效的 C。若此前扩容或旧引用先被清掉，则这条覆盖链不成立。
建议：复制数组，保留原对象指针
// GiveupTarget 中，替换直接共享切片的语句
curTarget.SetEndAttackInfo(
    append([]*BatCtx(nil), curTarget.GetWhoAttack()...),
)

// 结果：两份独立的数组，元素指向原来的战斗对象
WhoAttack     → 数组① [A指针 | B指针]
EndAttackInfo → 数组② [A指针 | B指针]
这里不需要深拷贝整个 BatCtx。不要向旧名单逐个追加 &BatCtx{TroopID: ...}：会改变替换语义、累积重复记录，旧数组仍可能共享，并且丢掉 PlayerID 等字段。龙巢宝箱相关读取方确实使用 EndAttackInfo 元素的 PlayerID。
如果没有其他赋值路径，新建 BatCtx 的 EndAttackInfo 默认是 nil；第一次 append(nil, A) 会分配独立数组，不会产生上述覆盖。
建议尚未实施。仍需评估其他直接赋值路径、遗漏收尾以及历史失效关系的清理。不能直接手改生成 accessor，也不能把所有相似赋值都认定为相同故障。
