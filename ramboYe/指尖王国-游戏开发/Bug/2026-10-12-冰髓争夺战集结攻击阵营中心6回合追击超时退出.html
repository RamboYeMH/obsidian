结论

集结 7695703180996225411 不是被打光，也不是被遣返。它到达阵营中心时和其他部队重叠，atkTroopMove 把它挪到了一个超出追击半径的站位：距离 16786，追击半径 16500。防守方驻防不动，集结追了 MaxChaseRound=5 回合还没回到范围内，于是 “追击时间太长，结束战斗”，带兵存活退出。战报照常发出，所以战报里只有前几回合。

挪出范围的原因：站位环是冰霜怪（阻挡半径 2000）先生成并缓存在防守方身上的，半径 17000；玩家部队阻挡半径 1500，追击半径只有 16500，复用这个环就会被挪出范围。

根因

站位环是冰霜怪（NPC）生成后缓存在防守方身上的，半径按 NPC 的阻挡半径算成了 17000；玩家部队复用这个环，被挪到 16500–17000 之间，超出了自己 16500 的追击半径。

1. 环只生成一次，之后一直复用

atkTroopMovePaths（ctl_battle_move.go:249）用当前进攻方的 GetBattleRadius 算出 top，再调防守方的 BatCtx.GetRangeCoord(top, …)。而 GetRangeCoord（battle/battlectx.go:309）只在 len(RangeCoord) <= 0 时才生成环，之后直接返回缓存，后来者传入的 top 不起作用。

清空环的地方只有两处，对驻防在阵营中心、持续被攻打的防守集结都不生效：

  • battleStart（battle/battlectx.go:935）：开头 selfIn && opIn 时直接 return；防守方一直在战斗中，新进攻方到达时也已把目标设成它，所以不会清空。
  • checkAtkTroopMoveChose（ctl_battle_move.go:221）：只在行军途中检查时清行军部队自己的环；防守方驻防不行军，永远调不到。

  • 玩家集结的追击半径 = 1500 + 5000 + 10000 = 16500（与日志一致）。它自己算的站位半径也是 16500，如果环是它生成的就不会出问题。

4. “防守集结”的生命周期与环的生成者

阵营中心的驻防编队平时是一支支独立编队。第一支进攻部队到达时，TroopAtkUnionCenterFactoryArrive（ctl_union_center.go:360）发现 DefenderID 对应的集结不存在，就调用 CreateUnionCenterDefendRally（:253）/ newDefendRally（:310），把驻防编队合成一个临时“防守集结”。这个集结的阻挡半径等于中心的阻挡半径，并带着全新的 BatCtx，RangeCoord 为空。防守集结战斗结束时，DefendUnionCenterEnd（:1335）会解散它：打输了解散并让中心扣 1 点耐久；打赢了且已没人在打它也解散。下一波进攻到达时再新建，环随之重新生成。

环由“新防守集结出现后，第一个到达时发生重叠的进攻单位”生成（atkTroopMoveCoordIsOverlap 为真才会进入 atkTroopMovePaths；日志打 no paths 的那次调用也已经生成了环）。今天 20:00 后 cross7 的 7 个防守集结：

复现步骤（修复前的代码）

关键是：先让冰霜怪生成 17000 的环，再让玩家集结在重叠的情况下到达。“挪位后超出追击范围”稳定复现；最终是否因追击超时退出战斗不一定每次出现。

前置条件

  • 冰髓争夺战处于战斗阶段（进攻阵营中心需要 IsIceContestInBattlePhase 通过）。
  • 防守方阵营（如阵营 2）的阵营中心里有玩家驻防编队。
  • 进攻方阵营（如阵营 3）准备 2–3 个能发起集结的账号。

步骤

  1. 让防守集结重新开始：确认当前没人在打这个阵营中心，等上一波的防守集结解散，下一支到达会新建防守集结，环为空。
  2. 先刷两只冰霜怪，让 NPC 生成环：
    gmspawnicefrost 3 2 10 // 进攻阵营 防守阵营 [出怪倒计时秒]，目标自动是防守方阵营中心 gmspawnicefrost 3 2 12
    第一只到达时不重叠，不生成环；第二只到达时与第一只重叠，触发 atkTroopMove，按 NPC 阻挡半径 2000 生成 17000 的环。日志应有 atkTroopMove unit <冰霜怪ID> ... roundPoints [...]。重叠后第一个触发挪位的必须是冰霜怪，若玩家部队先在重叠时到达，生成的是 16500 的环，复现不出来。
  3. 冰霜怪还在打的时候，让玩家集结到达：防守集结一直在战斗中，环不会被清空。从冰髓门出来的到达点基本固定，几乎必然与场上单位重叠。可以多发几支（单队、集结都发）。

根治方案（已改，未提交，计划下个版本）

只改 game/wmap/internal/ctl_battle_move.go 的 atkTroopMovePaths（+18 / −3 行）：缓存的环仍用来分配站位（角度和占用标记不变），但选路和移动前，把环上的点沿原方向缩放到本部队自己的站位半径。

rounds := batCtx.GetRangeCoord(top, tarCoord, nv1Max) // 预设点缓存在目标身上, 半径由首个生成者决定(如NPC阻挡半径更大), 按本部队的半径缩放后再选路, // 否则会被挪出本部队的追击范围 ownRounds := scaleRangeCoords(rounds, tarCoord, radius) ... // 找离 behind 最近的点、atkTroopMovePresetPaths 选路都改用 ownRounds path, index := wmap.atkTroopMovePresetPaths(unit, tarCoord, idx, ownRounds) if len(path) > 0 { // 占用标记按缓存中的原始点记录 batCtx.UseRangeCoord(rounds[index]) return path } // scaleRangeCoords 将围绕 center 的预设点沿原方向缩放到 radius 半径上 func scaleRangeCoords(rounds []geo.Coord, center geo.Coord, radius int32) []geo.Coord { ret := make([]geo.Coord, len(rounds)) for i, c := range rounds { vec := geo.NewVector(center, c) length := vec.Length() if length <= 0 { ret[i] = c continue } ret[i] = vec.Trunc(float64(radius) / length).ToCoord(center) } return ret }

效果

  • 玩家部队（阻挡半径 1500）挪到自己 16500 的环上；螺旋路径只走到 (n-1)/n，终点一定 ≤ 16500，在追击范围内且不与他人重叠。
  • NPC（阻挡半径 2000）缩放到 17000，与原来的环相同，行为不变。
  • 与环由谁生成、中途是否被清空重建无关，都能保证终点不超出本部队的站位半径。
  • 同一角度的站位 NPC 和玩家会站在不同半径上（17000 / 16500）；占用仍按原始点记录，同一角度 20 秒内只分给一个单位，不会叠在一起。

为什么不选其他方案

  • 记下生成半径、不同就重建环：多个不同半径的单位轮流到达时环会反复重建，占用标记丢失，反而更容易重叠。
  • 驻防目标时终点超出追击半径就不移动（中途加过的兜底）：已按要求移除，atkTroopMove 本身无改动。
注意 移除兜底后，若以后把 10131008（触发战斗半径）调得比 10131007（射程）大，或某玩法驻防集结的阻挡半径比所驻防建筑大（atkTroopMovePaths 取两者较大者，BattleChasingDis 固定用建筑），站位半径会再次超过追击半径，问题会重现且没有日志提示。

性能影响：可忽略

  • 只在部队到达且与他人重叠时触发，事件驱动，不在每秒的战斗 tick 里。
  • 每次多一个切片分配（环上点数 8 / 16 / 40，阵营中心为 40 个点，约 320 字节）和每点一次开方、一次除法；同函数里本就对每点算一次距离，后续 atkTroopMovePresetPaths 的螺旋路径和碰撞检测要重一到两个数量级。
  • 不改变环的生成、缓存、清空频率，不增加锁、日志或网络调用，无常驻内存。

修复后验证

  • 按上面的复现步骤操作：玩家部队挪位后不再出现 battleChasing outOfRange 和 追击时间太长，atkTroopMove 终点到中心的距离 ≤ 16500
  • 回归野外：多支部队同时打同一个野怪或玩家部队，挪位后站位正常、无明显重叠
