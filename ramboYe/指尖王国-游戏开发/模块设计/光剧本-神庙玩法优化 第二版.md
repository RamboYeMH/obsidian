# 光剧本 - 神庙玩法优化

## 一、优化目的

### 1.1 原先的神庙玩法存在以下问题

- a. 探索→攻打Boss的玩法链路，与已有的普通玩法太类似，没有新意
- b. 单编队造成伤害最高的，打5次伤害也基本最高。排行榜也就相对固定了，打那么多次没有太大意义，使得玩法太拖沓
- c. 遗迹建筑有很多个，有些建筑还很远，使得玩家需要花费太多时间在没有太大趣味的玩法上
- d. 攻击Boss的编队无法被敌人攻击，没有PVP属性，使得这段时间战场内没有阵营冲突（除开战旗、龙巢的争夺）

### 1.2 原玩法概述
  
- a. 神庙阶段性开放，每个阶段开放1-2个
- b. 玩家每个神庙可探索1次（不限制阵营，可到达就行），神庙增加探索编队战力相关的进度
- c. 神庙进度达到100%，出现boss
- d. 玩家可攻打每个Boss 5次。根据伤害排行发放排行榜奖励
- e. 累计伤害还有赛季累积奖励
- f. Boss生存时间结束，该神庙永久关闭

## 二、核心概念

| 术语       | 定义                                                              |
| -------- | --------------------------------------------------------------- |
| 神庙       | 每个阵营各自拥有的独立世界地图建筑；每轮只激活当前防守方对应神庙。                               |
| 神庙Boss   | 当前神庙对应的共享血量Boss，是第二阶段唯一主目标。即神庙中的NPC                             |
| 封印区域     | 第一阶段同时开放的3个封印区域，占领规则与战旗有较高重合度，不可攻击或驻防的建筑。三个封印区域都是独立的建筑,进攻方需要去占领 |
| 破封进度     | 进攻方第一阶段累计获得的全局进度，只增不减，范围0%—100%。                                |
| 封印护盾     | 未完成破封进度线性转化的Boss额外耐久，位于Boss本体血量之前。                              |
| Boss战斗区域 | 第二阶段以神庙Boss为中心、地图明确显示边界的有效活动PVP区域。                              |

| 参考DPS    | 同战力档参考进攻阵营在无PVP干扰下的持续Boss总输出。                                   |

## 三、核心循环

### 3.1 第一阶段：阵营组织与优势争夺

双方围绕3个封印区域分兵、支援、转点和PVP。进攻方正式控制区域后持续累计全局破封进度；防守方通过夺回区域暂停对应产出。破封进度决定第二阶段Boss的初始封印护盾。即进攻方需要去占领封印区域,封印区域的进度是只增不减,当达到100%时则破除一个区域,防守方

### 3.2 第二阶段：阵营决战与优势兑现

封印区域全部停用，进攻方需要去进攻神庙boss。进攻方必须在固定时间内打破剩余护盾并击败Boss本体；防守方不能操作Boss，只能通过PVP击退、消耗或迫使进攻方抽调输出,这里是自由的pvp 防守方需要攻击进攻方的部队以达到阻止进攻方攻击神庙boss的行为
封印区域:在生成地图时就已经创建好,在战斗一阶段时开放防守方的
### 3.3 战略取舍

- **战斗第一阶段**：进攻方需要去进攻防守方封印区域并完成占领才能减少战斗阶段第二轮boss的盾
- **战斗第二阶段进攻方**：进攻方去进攻神庙boss防守方防守
- **战斗第二阶段防守方**：集中击杀高输出队，或扩大区域PVP压力、压缩整体有效输出时间。
3.4 记录
需要记录每一轮的战斗情况与冰髓战差不多,因为需要展每一轮的情况,主要是封印区域的攻防情况,和神庙boss的情况

## 四、开放规则与活动状态

### 4.1 单轮结构（由配置决定）

- 赛季内预计开放8轮，每轮在不同日期进行。两个阵营中各为攻守方
- 第一轮在阵营A或阵营B其中一方的神庙进行，另一方进攻；第二轮启用另一处神庙并交换攻守。以此类推
- 每轮使用相同基础配置，但对应不同神庙建筑与Boss实体
- 每轮的破封、区域归属、Boss、护盾、贡献、排行榜、里程碑和结算记录完全独立
- 上一轮玩法状态不传递至下一轮
- 每轮分别判定胜负、发放奖励；不设置总比分、综合胜负、本期冠军或跨轮表现比较

### 4.2 神庙激活规则

- 每轮仅激活当前轮对应神庙的封印区域、Boss和战斗区域
- 非当前轮或已结束轮次的神庙不参与活动：封印区域不占领、不产出进度，Boss不可选取或攻击
- 非活动神庙周边的PVP仍按普通开放世界战斗处理，但不产生活动贡献

### 4.3 单轮状态流

| 状态 | 进入条件 | 可执行活动行为 | 退出条件 |
|---|---|---|---|
| 预告期 | 当前时间早于本轮开始时间 | 可在世界地图提前布阵；不产生活动贡献 | 到达本轮开始时间 |
| 战斗期-第一阶段 | 本轮开始 | 战旗占领、封印区域PVP、累计破封进度 | 破封100%或30分钟截止 |
| 战斗期-第二阶段 | 第一阶段结束 | 进攻方攻击Boss/防守编队；防守方攻击进攻编队 | Boss本体0血或30分钟截止 |
| 已结算 | 第二阶段结束 | 查看结算与领取奖励 | 无 |
| 展示期 | 第二阶段结束 | 查看结算与领取奖励 | 跨到下一天0点时 |
| 关闭期 | 最后一轮的展示期结束 | 查看总览界面 | 远征结束 |

### 4.4 活动前布阵

- 活动开始前不清场、不传送、不强制返城
- 第一阶段开始时，已位于封印区域内的编队点击破除按钮后立即按占领规则参与占领
- 活动开始前发生的PVP不计活动贡献
- 第二阶段开始前Boss不可选取、不可受伤，也不会攻击玩家
- 第二阶段开始时，区域内编队仍需玩家主动选择Boss或敌方目标，系统不自动开战

### 4.5 参战与成本

- 玩法在现有世界地图直接进行，不创建独立副本，不设置报名、参战名额或人数上限
- 玩家可以在第一阶段或第二阶段任意时刻直接加入，不要求参加第一阶段才能进入第二阶段
- 第一阶段优势归本阵营全体共享，不限制第二阶段战斗权限；玩家缺席某阶段只影响其个人贡献和奖励进度
- 单次出征可以按自由行军规则连续经历多场战斗，战斗后剩余血量自然影响后续有效伤害和贡献
- 行军速度、出征队列、战损、战败返程、伤兵、治疗和再次出征均沿用世界规则
- 活动不提供新增兵力、即时复活、损耗减免或额外出征队列

## 五、玩法规则描述

### 5.1 第一阶段规则

#### 5.1.1 基础结构

- 第一阶段时间上限：30分钟（暂定）；配置待定
- 3个封印区域同时开放、可同时占领
- 三个区域面积、基础占领条件和破封进度产出一致，围绕神庙分散布置
- 封印区域本身无血量，不接受建筑攻击，也不使用单队驻防

#### 5.1.2 战旗占领

基本沿用现有战旗占领规则：

1. 区域内双方阵营编队比较，未移动的、最高战力的编队所属阵营成为当前占领方
2. 当前占领方在区域内的去重玩家数量决定占领速度。每名进攻方玩家每秒提供的进度配置待定
3. 同一玩家在同一区域放置多支编队，占领人数只计1人
4. 占领条推进、正式归属、空置、同战力、进出、换边及其他边界全部沿用现有状态机
5. 只有区域正式归进攻方占领中时，才产出破封进度；其他状态均不产出
6. 因为破封时间有限，不设置提供破封进度人数的上限

#### 5.1.3 破封进度

- 破封进度为进攻方全阵营共享的全局累计值，范围0%—100%
- 每个进攻方正式控制区域的基础产出为 `100%÷30=3.333…%/分钟`，3处线性叠加；界面可显示为3.333%
- 控制0处时进度完全停止，不存在自动增长或最低保底
- 进度只增不减；防守方不能扣除已获得进度
- 持续控制1、2、3处时，连续数学下的理论完成时间分别为30、15、10分钟。由于截止时间 `T` 当刻生效的结果不计入，整阶段仅控制1处不能保证在截止前完成100%，最终值以服务端 `T` 前冻结状态为准
- 平均控制1.5处时约20分钟完成；平均控制0.5处并持续至超时时，最终约50%

#### 5.1.4 第一阶段结束

- 破封进度在截止时间前达到100%时，第一阶段立即结束并进入第二阶段
- 未达到100%时，30分钟到达后冻结当前进度并强制进入第二阶段
- 不加时，不存在"破封失败后取消第二阶段"
- 第一阶段不产生单轮胜负

#### 5.1.5 第一阶段切换处理

- 第一阶段结束时，3个封印区域立即失效并停止产出
- 未结束的世界行军和玩家PVP不强制中断、传送或返城，继续按通用规则结算
- 切换后发生在旧封印区域的战斗不再产出第一阶段贡献
- Boss在第二阶段开始时开放攻击

#### 5.1.6 破除封印时，编队标记的显示

- 主要沿用战旗的规则
- 攻、防双方中，封印建筑有限范围内，战力最高编队所处阵营为实际控制方；且该最高战力编队需要被标识

### 5.2 第一阶段对第二阶段的影响

第一阶段的结果，将会给第二阶段的Boss增加一定数量的护盾（可视为额外血量）

#### 5.2.1 转化公式

设：

- `P` = 第一阶段最终破封比例，取值0—1；
- `Hboss` = Boss本体血量；
- `Rshield` = 满封印护盾占本体比例，首版为25%。

则第二阶段初始护盾为：

```
Hshield = Hboss × Rshield × (1 - P)
```

示例：

| 最终破封 | 初始护盾占Boss本体 |
|---|---|
| 0% | 25% |
| 25% | 18.75% |
| 50% | 12.50% |
| 75% | 6.25% |
| 100% | 0% |

#### 5.2.2 护盾规则

- 护盾为Boss共享本体血条之前的纯额外耐久
- 增加的护盾值不影响Boss对玩家造成的伤害
- 所有进攻编队共同削减同一护盾
- Boss在护盾存在时正常反击；伤害公式沿用现有Boss战
- 单次伤害超过剩余护盾时，超出部分按既有底层逻辑转入Boss本体
- 护盾不恢复，防守方不能治疗、增盾、攻击或控制护盾
- 护盾耗尽后直接进入Boss本体承伤，不新增第三阶段
- 第二阶段时长固定，不因第一阶段结果增加时间或伤害倍率

### 5.3 第二阶段规则

#### 5.3.1 基础结构

- 第二阶段基础时长30分钟，第一阶段提前结束，则将剩余时间加到第二阶段
- Boss是唯一主目标；第一阶段封印区域全部停用
- 不新增占点、采集、增益、护送职业、拦截技能或攻击队列
- 以Boss为中心配置一个地图持续可见的Boss战斗区域，用于活动PVP贡献判定

#### 5.3.2 Boss交战流程

进攻方攻击Boss使用已有通用流程：

1. 选择Boss目标
2. 选择出战编队
3. 编队出发
4. 编队在世界地图行军，途中可被防守方攻击
5. 接触Boss后进入持续战斗，期间仍可被防守方攻击
6. 编队与Boss依据战力互相造成伤害；多支编队可同时攻击共享护盾和血量
7. 任一方血量归零后结束该编队与Boss的战斗

正在攻击Boss的编队遭到玩家PVP攻击时，Boss战不暂停；该编队同时承受Boss与敌方伤害。编队0血后退出Boss战，并按现有战败规则处理。

#### 5.3.3 开放目标选择

- 进攻方可持续攻击Boss，也可主动脱离Boss战并按正常行军流程攻击防守编队
- 脱离和改目标不是瞬时切换，不提供无敌、免伤或免费位移
- 防守方可攻击任意进攻编队，包括行军中和攻击Boss中的编队
- 防守方不能直接攻击、治疗、增盾或控制Boss及封印护盾
- PVE与PVP并行结算，玩家PVP不会暂停Boss战

#### 5.3.4 第二阶段结束

- Boss本体在截止时间前降至0血：进攻方立即获胜，本轮立即结束
- 截止时间到达时Boss本体仍有血量：防守方获胜，本轮强制结束
- 仅打破封印护盾不算击败Boss
- 结束时立即冻结胜负、贡献、攻坚榜和里程碑，Boss关闭交互并停止造成或承受伤害
- 正在攻击Boss或前往Boss的编队按现有"目标失效"逻辑处理，不新增返还或补偿
- 未结束的玩家PVP继续按世界规则结算，但结束后的伤害不再计活动贡献，也不能改变已冻结胜负

### 5.4 胜负与结算

#### 5.4.1 单轮胜负

| 条件                 | 结果            |
| ------------------ | ------------- |
| Boss本体在第二阶段截止前降至0血 | 进攻方胜利，立即结束    |
| 第二阶段截止时Boss本体仍有血量  | 防守方胜利         |
| 仅护盾降至0，Boss本体仍存活   | 不产生胜负，继续战斗    |
| 第一阶段达到或未达到100%     | 只影响护盾，不直接产生胜负 |

#### 5.4.2 结算

- 每轮独立判定并独立发奖
- 不比较两轮击杀时间、Boss剩余血量、贡献或总比分
- 允许同一阵营赢两轮，也允许双方各赢一轮
- 两轮结束页面仅并列展示各轮结果

#### 5.4.3 结算邮件整理

| 序号 | 模块 | 邮件ID | 邮件名称 | 发送情况 | 是否包含奖励 | 邮件内容文本赋值逻辑 |
|---|---|---|---|---|---|---|
| 1 | 匹配 | 17180028（全局表获取：`LeagueWar_Match_DowngradeMail`） | 降级通知邮件 | 联盟上一轮有参赛资格，且在上一轮（第2、第3轮）中联盟积分=0，且没有占领王座。在活动结束时为联盟成员发放 | 否 | `{0}`：当前参加的巅峰领地活动的轮次数；`{1}`：战场名称 |

> 该表在原始需求中仅有第1项，其余邮件（个人参与奖补发、阵营胜负奖励）见 6.1、6.2，邮件ID待定。

### 5.5 展示期

- 战斗期-第二阶段结束后，进入展示期
- 展示期持续时长为：战斗期-第二阶段结束后——当天跨0点时
- 主要用于展示排行榜、奖励预览：
  - 排行榜的重置时间点为"当天跨0点时"
  - "奖励入口和预览内容"的改变时间为"当天跨0点时"
  - 进攻/防守方阵营信息的改变时间为"当天跨0点时"
  - "战况界面"的关闭时间为"当天跨0点时"

### 5.6 关闭期

- 最后一轮的展示期结束，进入关闭期
- 关闭期持续时长为：最后一轮的展示期结束——当前远征赛季结束

## 六、奖励设计与发放规则

### 6.1 个人参与奖

- 增加本活动新增积分、本活动新增任务
- 完成任务获得积分，积分到达一定数值需求后解锁奖励。共有6档奖励
- 奖励解锁后可手动领取。未领取的已解锁奖励在单轮玩法结束后通过邮件补发（补发邮件id待定）

### 6.2 阵营胜负奖励

- 单轮根据胜负结果发放奖励
- 双方阵营均会发放：胜利阵营发放胜利奖励、失败阵营发放失败奖励
- 该奖励有发放条件，需要新增个人积分达到一定数值需求的阵营成员才会获得（邮件id待定）

### 6.3 攻坚伤害榜奖励

- 仅进攻方参与，第二阶段开放并实时刷新
- 统计护盾和Boss本体的全部非溢出有效伤害，未击杀也正常结榜发奖
- 仅收录产生过有效攻坚伤害的玩家
- 排名并列及排序顺序沿用现有排行榜规则
- 第二阶段结束时冻结最终榜单

## 八、与现有实现的关系

原有 `LightTemple`（`ctl_light_temple*.go` / `light_temple_mgr.go` / `mcity/light_temple.go`）是旧版"探索进度→单Boss→限次攻打"玩法，未被本次优化复用；决策结果是拆分为独立的**神庙攻防战（TempleWar）**状态机，与旧实现并存、互不影响。

### 8.1 整体架构：对齐冰髓争夺战（IceContestMgr）模式

全局只有一个"当前阶段"指针，沿配置表 `NextId` 单链推进（预告→第一阶段→第二阶段→已结算，循环N轮）；到期由 1s ticker 检测推进，Fire 通用阶段变化事件后按 `StageId` 分发到具体处理函数（观察者模式）。

与冰髓争夺战的差异：`TempleStageCfg` 的一个阶段（尤其"预告"）可能通过 `Group` 字段同时挂多个 `TempleGroupCfg` 战场（例如同一轮2个神庙同时开战），因此每个战场维护自己独立的 `Phase1EndTs`/`Phase2EndTs`：全局阶段时钟给出该阶段的"默认/上限"时长，但破封进度提前100%的战场可以提前结束第一阶段（5.1.4），提前的剩余时间叠加到自己的第二阶段（5.3.1）；全局阶段到期时仍未完成的战场被强制冻结/结束。

### 8.2 配置表

| 配置表 | 作用 | 关键字段 |
|---|---|---|
| `TempleStageCfg`（`gdconf/conf_templestage.go`） | 全局阶段链，一行=某轮的某个子阶段 | `Id`/`NextId`（链指针）、`Round`（轮次）、`StageId`（预告/Phase1/Phase2/已结算）、`SustainTime`（本阶段持续时间，**Phase1的30分钟尚未填值**）、`Group`（本阶段挂载的 `TempleGroupCfg` 分组） |
| `TempleGroupCfg`（`gdconf/conf_templegroup.go`） | 一行=一个战场，圈定攻守阵营、作战区域与Boss | `Group`（归属分组）、`AtkCamp`/`DefCamp`（进攻/防守阵营）、`BattleArea`（对应远征 `StateId`）、`BossId`（Boss的 `D2NpcTroopClassCfg` 配置ID，等级暂固定为1，数据未填，需策划配置） |

### 8.4 实现进度

- **里程碑一（已完成）**：阶段链推进；预告期按 `TempleGroupCfg` 生成神庙场地与3个封印区域；第一阶段封印区域占领复用现有战旗（`AreaBuild`）占领状态机，按占领区域数线性累加破封进度（`TemplewarSealProgressRatePerZone`），100%或超时即冻结进入第二阶段并回收封印区域。
- **里程碑三（已完成）**：第二阶段开局 `createTempleWarBoss` 按 `TempleGroupCfg.BossId` 刷出Boss（`mtroop.NewStaticNpcTroop`，与光剧本旧版 `createLightTempleBoss` 同构），并按本文档5.2.1公式（`Hshield = Hboss × Rshield × (1-P)`，`Rshield` 取 `TemplewarShieldRatio`，首版25%）计算护盾写入 `TempleWarBattleState.ShieldHp`。突击流程（`ctl_templewar_action.go`）与光剧本旧版一致：行军目标是 `TempleWarSite` 本身，抵达后从 `site.DefenderID` 取出当前Boss发起 `troopAtkTroop`；战斗结算里直接判定 `battle.GetBattleResult` 是否为Boss阵亡，阵亡则立即调用 `endTempleWarBattle` 判进攻方胜利（doc 5.3.4），**不需要额外的每秒轮询**——比此前设想的"对称于第一阶段、新增周期性`TempleWarBossHpTick`"更简单：Boss死亡本身就是战斗结算的同步产物，没有必要每秒轮询一个只会在结算那一刻改变的状态。超时未死亡的战场，仍按原设计由全局 `onTempleWarToSettled` 兜底判防守方获胜。
- **已知简化（护盾与Boss输出耦合）**：战斗引擎里部队的攻击力由 `GetAtk()` 直接对其 `SoldierInfo.CurPower` 求和算出，即"血量"与"攻击力"共用同一份数值，没有独立的纯防御层可以单独挂护盾。当前实现是直接按护盾比例放大Boss全部兵种的 `Power`/`CurPower`（`createTempleWarBoss` 内），代价是护盾存在时Boss的输出也会同步偏高，与本文档5.2.2"护盾不影响Boss输出伤害"不完全一致——已与策划确认，作为可接受的简化先上线。如需精确隔离，需要在 `battle/lineup.go` 的伤害结算（`calculateAndApplyDamage`/`calcHurtDead`）里单独开一个不参与 `GetAtk()` 计算的护盾扣血层，属于对全游戏共用战斗核心的改动，风险和工作量都显著更高，留待有实际需要时再评估。

### 8.5 客户端协议（对照冰髓争夺战）

冰髓战的客户端面板较重（宣战/取消宣战、进攻方分组、防守方分组、排名分发等），源于它有联盟对联盟的"宣战"元层，神庙攻防战没有这一层（攻守阵营由 `TempleGroupCfg` 静态配好，不需要宣战），因此只按"让客户端能看到状态变化、不用轮询"这个核心诉求对齐，未整体照搬：

| 消息 | 类型 | 对照冰髓战 | 说明 |
|---|---|---|---|
| `TempleWarInfoReq`/`Ack` | 请求/应答 | `ExpIceContestOverviewReq`/`Ack`（单点查询） | 已在里程碑一提供；本次补充 `ShieldHp`/`BossNpcID`/`Winner` 三个里程碑三字段 |
| `TempleWarPhaseChangeNtf` | 广播 | `C2PIceContestPhaseChangeNtf` | 全局阶段一变化就推（`PhaseCfgId`+`PhaseEndTime`），用于客户端刷新计时器，payload很轻 |
| `TempleWarOverViewNtf` | 广播 | `IceContestOverViewNtf` | 携带当轮全部战场（`repeated TempleWarBattleInfo`）的完整状态；在全局阶段切换、任一战场提前进入第二阶段、任一战场分出胜负这三类时机推送（`broadcastTempleWarOverview`），客户端据此刷新总览面板 |
| `PropertyUnion.templeWarSiteInfo`（`TempleWarBattleInfo`） | 地图单位属性 | `PropertyUnion.LightTemplInfo` | 挂在 `TempleWarSite` 本身的地图单位广播上，使已有的 `BroadcastUnitNtfImpl(site)` 调用点顺带把状态带给客户端，不需要额外协议 |

`TempleWarBattleInfo` 同时兼作总览列表项和地图单位属性（两处共用同一结构，字段含义见 `struct.proto`），字段与 `TempleWarInfoAck` 基本对齐（多一个 `UnitID` 便于总览列表直接定位战场）。
