# 设计模式实践：开闭原则与接口驱动设计

## 我的核心感悟

> 开闭原则一定要遵循。代码写完、QA 测完之后，它就应该进入稳定状态。后续增加功能时，应通过预先识别的扩展接口接入，而不是不断在原有代码末尾追加分支。
>
> 面对一个系统时，首先应该思考如何拆分、有哪些职责、哪些地方需要接口和不同实现，而不是一开始就把存储结构想完，再一股脑把函数写完。

这段感悟的本质，是把开发思路从“完成当前功能”提升为“建立一个可以持续演进的结构”。

## 一、怎样理解开闭原则

开闭原则（Open–Closed Principle，OCP）是：

> 软件实体应该对扩展开放，对修改关闭。

“关闭”不是说代码提交后永远不能修改。Bug、规则错误、安全问题和错误抽象仍然必须修复。更准确的理解是：

- 已经通过测试并稳定运行的主流程，不应因为每次新增业务类型而反复修改。
- 新功能优先通过新增实现、注册配置或组合已有能力完成。
- 修改旧代码应该是纠正旧行为，而不是扩展新行为的默认方式。

判断设计是否符合开闭原则，可以问一个直接的问题：

> 增加一种同类功能时，我是在增加一个独立实现，还是必须进入稳定主流程继续加 `if/switch`？

如果每增加一种玩法、活动、建筑或行军行为，都必须修改同一个核心函数，那么这个函数实际上同时承担了“流程编排”和“所有业务类型的具体规则”，变化会不断向稳定代码扩散。

## 二、先寻找变化点，再设计接口

接口不是越多越好，也不是为了无法预测的未来预先搭框架。接口应该围绕已经出现、或者需求中明确可见的变化轴建立。

设计一个系统前，先回答四组问题：

1. **稳定的主干是什么**
   - 哪些步骤无论业务类型如何变化都不会改变？
   - 哪些校验、编排、日志、事务边界可以由主流程统一负责？

2. **可能变化的行为是什么**
   - 是否存在多种计算规则、处理方式或目标类型？
   - 新增一种行为时，是否能作为独立实现接入？

3. **状态怎样流转**
   - 对象是否有明确的创建、运行、暂停、完成、失效等生命周期？
   - 状态迁移是否合法，应该由谁保证？

4. **系统边界在哪里**
   - 哪些是数据库、缓存、网络、消息等外部细节？
   - 领域逻辑是否可以不依赖具体存储而单独测试？

在这些问题有答案之后，再决定数据如何落库、函数如何组织。存储是实现细节，不应反过来决定领域模型的职责边界。

```mermaid
flowchart LR
    A[理解需求与业务规则] --> B[识别稳定主干]
    B --> C[识别变化轴]
    C --> D[定义最小接口与契约]
    D --> E[实现策略/状态/事件处理器]
    E --> F[通过工厂或注册表装配]
    F --> G[补充契约测试]
    G --> H[稳定主流程]
    H -->|新增功能| E
```

## 三、从追加分支变为扩展实现

### 容易出现的写法

一个核心函数根据类型处理所有业务。每次新增类型，就继续扩大 `switch`：

```go
// ExecuteActivity 根据活动类型执行对应逻辑。
// 反例：新增活动必须修改此函数，稳定流程会被反复打开。
func ExecuteActivity(activityType ActivityType, ctx *Context) ErrCode {
    switch activityType {
    case ActivityTypeExchange:
        return executeExchange(ctx)
    case ActivityTypeRank:
        return executeRank(ctx)
    case ActivityTypeLottery:
        return executeLottery(ctx)
    default:
        return ErrCodeInvalidActivity
    }
}
```

问题不只是 `switch` 很长，而是：

- 核心函数知道所有具体类型，职责不断膨胀。
- 新功能必须改旧代码，容易影响已通过 QA 的分支。
- 多人并行开发时集中修改同一文件，冲突概率高。
- 很难只针对某一种行为做隔离测试。

### 更符合开闭原则的写法

把变化行为抽象为策略接口，通过注册表完成类型与实现的装配：

```go
// ActivityHandler 定义活动行为必须遵守的最小契约。
type ActivityHandler interface {
    Handle(ctx *Context) ErrCode
}

// ActivityHandlerFactory 创建独立的活动处理器。
type ActivityHandlerFactory func() ActivityHandler

var activityHandlerFactories = map[ActivityType]ActivityHandlerFactory{}

// RegisterActivityHandler 注册活动类型对应的处理器工厂。
// 同一类型只能在初始化阶段注册一次。
func RegisterActivityHandler(
    activityType ActivityType,
    factory ActivityHandlerFactory,
) {
    activityHandlerFactories[activityType] = factory
}

// NewActivityHandler 根据活动类型创建处理器。
// 未注册类型返回 false，由调用方转换为统一业务错误码。
func NewActivityHandler(activityType ActivityType) (ActivityHandler, bool) {
    factory, ok := activityHandlerFactories[activityType]
    if !ok {
        return nil, false
    }
    return factory(), true
}

// ExecuteActivity 负责稳定的活动执行流程。
// 具体规则由已注册的处理器实现，主流程不感知具体活动类型。
func ExecuteActivity(activityType ActivityType, ctx *Context) ErrCode {
    handler, ok := NewActivityHandler(activityType)
    if !ok {
        return ErrCodeInvalidActivity
    }
    return handler.Handle(ctx)
}
```

以后增加一种活动，主要工作变成：

1. 新增一个 `ActivityHandler` 实现。
2. 注册对应工厂。
3. 增加该实现的契约测试。

稳定的 `ExecuteActivity` 不需要因为新增类型而修改。

## 四、不同变化应该使用不同模式

设计模式不是目的，而是隔离变化的工具。先判断变化性质，再选择结构。

| 变化场景 | 优先考虑 | 解决的问题 |
|---|---|---|
| 同一操作存在多套算法或规则 | 策略模式 | 将行为差异从主流程中拆出 |
| 同一接口存在多种实现对象 | 工厂 / 注册表工厂 | 统一创建和装配，避免调用层依赖具体类型 |
| 对象有明确生命周期和迁移约束 | 状态模式 / 状态机 | 收拢状态行为，禁止跳转逻辑散落 |
| 状态变化后需要通知多个模块 | 观察者 / 领域事件 | 解耦发布方与多个消费方 |
| 领域逻辑需要读写数据库、缓存或远程服务 | Repository / Port-Adapter | 让业务依赖抽象，而不是依赖存储细节 |

组合这些模式时，仍要保持调用链清晰。例如：

- 工厂负责创建策略，不负责执行业务。
- 策略负责单类规则，不负责系统级流程编排。
- 状态机负责迁移约束，不直接耦合所有通知接收者。
- 事件负责传递“发生了什么”，不把消费方逻辑塞回发布方。

## 五、“预留接口”不等于提前设计所有未来

开闭原则必须和 KISS、YAGNI 一起使用。

不建议：

- 只有一种实现、也没有明确变化迹象时，为每个函数都建立接口。
- 根据想象中的未来需求建立多层工厂、抽象基类和复杂插件体系。
- 接口包含大量当前实现并不需要的方法。
- 为了“通用”而把清晰的业务语义变成 `map[string]interface{}`。

建议：

- 已经存在两个及以上实现时，立即识别共同契约。
- 产品规划中明确会持续增加同类功能时，提前建立稳定扩展点。
- 核心流程频繁因类型分支而修改时，优先拆成策略或处理器注册表。
- 外部依赖导致业务难以测试时，在系统边界建立小接口。

好的接口不是“猜中未来”，而是准确表达当前系统中已经存在的变化方向。

## 六、推荐的系统设计顺序

### 1. 写清业务语言

先定义系统中的对象、动作、状态和约束，不从表结构开始讨论。

### 2. 划分职责

明确谁负责校验、谁负责状态变更、谁负责持久化、谁负责通知。一个模块只承担一类清晰职责。

### 3. 找到稳定主干与变化轴

把不会变化的流程留在编排层，把按类型变化的规则放入策略或处理器。

### 4. 定义最小契约

接口只包含调用方真正需要的方法，参数和返回值表达业务语义，不泄露具体存储结构。

### 5. 选择装配方式

多实现对象通过工厂或注册表创建；不要让稳定业务层直接 `new` 具体实现。

### 6. 最后确定存储

表结构、缓存 Key 和协议字段服务于领域模型，而不是决定领域模型。持久化细节通过边界接口接入。

### 7. 用测试保护契约

除具体实现测试外，还要验证所有实现都遵守共同契约，使新增实现不会破坏调用方假设。

## 七、设计评审清单

开始编码前：

- [ ] 能否用一句话说明模块的单一职责？
- [ ] 哪部分是稳定主干，哪部分会按类型或规则变化？
- [ ] 新增一种同类功能时，需要修改哪些旧文件？
- [ ] 接口是否来自真实变化点，而不是想象中的未来？
- [ ] 领域逻辑是否被数据库、缓存或协议结构绑住？
- [ ] 生命周期、状态迁移和失败回滚由谁负责？

提交 QA 前：

- [ ] 新行为是否通过新增实现接入，而不是扩大核心 `if/switch`？
- [ ] 工厂、策略、状态机、事件各自职责是否清晰？
- [ ] 接口是否小而专一，调用方是否依赖抽象？
- [ ] 是否存在跨模块直接调用造成的耦合或重入风险？
- [ ] 是否为新实现补充契约测试和边界测试？
- [ ] 是否同时满足 DRY、KISS、YAGNI，而非为了模式而模式？

## 八、最终原则

可以把这套思路浓缩为四句话：

1. **先设计变化的边界，再实现变化的细节。**
2. **让新增功能尽量新增代码，而不是修改稳定代码。**
3. **接口服务于明确的变化点，不服务于想象中的未来。**
4. **存储是系统边界的实现细节，不是业务设计的起点。**

开闭原则真正保护的，不只是代码形式，而是已经通过验证的业务行为。设计模式的价值，也不在于使用了多少模式，而在于新需求到来时，系统是否仍能以局部、可测试、低风险的方式演进。
